# Nintendo Switch 게임 한국어 패치 제작 워크플로

이 문서는 Nintendo Switch 게임의 **한국어 패치를 어떻게 설계하고 제작·검증·배포하는지**를 범용적인 관점에서 정리한 기술 노트입니다.

작성 기준은 실제 한국어 패치 배포 구조와 패처 운용 사례를 분석한 것이며, 특정 게임의 원본 데이터나 개인 정보는 포함하지 않습니다.

> [!IMPORTANT]
> 이 문서는 **본인이 합법적으로 보유한 게임에서 직접 준비한 파일**을 대상으로 한 번역·모딩 워크플로를 설명합니다.
> 게임 본편, NSP/XCI/NCA, 원본 RomFS, 키 파일, 복호화 키 획득 방법, 원본 이미지·음성·영상·대사 전체 덤프 등은 저장소에 올리지 않습니다.

---

## 1. 핵심 개념

Switch 한국어 패치는 보통 게임 전체를 다시 배포하는 작업이 아닙니다.

핵심 구조는 다음과 같습니다.

```text
합법적으로 준비한 원본 게임
        ↓
Base + Update가 반영된 clean RomFS
        ↓
텍스트 / 폰트 / UI / 영상 등 대상 분석
        ↓
한국어 자산 제작
        ↓
변경 파일만 재구축
        ↓
원본 ↔ 한국어 파일 차이 패치 생성
        ↓
사용자 PC에서 원본 검증 후 패치 적용
        ↓
Atmosphere / 에뮬레이터용 mod 폴더 출력
```

즉 배포자는 **원본 게임 데이터를 제공하지 않고**, 사용자가 자신이 보유한 게임에서 준비한 RomFS에 차이 패치만 적용하도록 만드는 방식이 안전하고 관리하기 쉽습니다.

---

## 2. 가장 먼저 해야 할 일: 지원 버전 고정

한국어 패치 제작 전에 반드시 지원할 원본 버전을 하나로 고정합니다.

확인할 항목:

```text
- Base Title ID
- Base 버전
- Update Title ID
- Update 버전
- 게임 화면에 표시되는 버전
```

패치 제작과 검증은 **항상 동일한 버전의 clean RomFS**를 기준으로 진행해야 합니다.

업데이트가 존재하는 게임은 Base만 덤프해서 작업하지 말고, 실제 플레이 시 사용되는 업데이트가 반영된 **effective / merged RomFS**를 기준으로 잡는 편이 안전합니다.

### 왜 중요한가

업데이트가 적용되면 다음이 달라질 수 있습니다.

- 스크립트 파일
- UI 이미지
- 실행 코드
- 폰트
- 파일 크기
- 압축 데이터
- 파일 해시

Base 기준으로 만든 패치를 Update가 적용된 게임에 사용하면 파일 불일치, 표시 오류, 프리징, 진행 불가 등이 생길 수 있습니다.

---

## 3. Clean RomFS 준비

분석용 원본은 반드시 **수정되지 않은 clean RomFS**를 사용합니다.

권장 조건:

```text
Base + 지원 Update 적용
다른 모드 없음
기존 한국어 패치 없음
전체(Full) RomFS
```

Skeleton 덤프처럼 실제 파일 내용이 빠진 구조는 패치 제작용 원본으로 적합하지 않습니다.

### 중요한 원칙

공개 문서에서는 RomFS를 준비하는 개념까지만 설명하고 다음 내용은 저장하지 않습니다.

```text
- 게임 원본 파일
- NSP / XCI / NCA
- prod.keys 등 키 파일
- DRM 또는 보호 기능 우회 절차
- 타인이 배포한 원본 다운로드 경로
```

---

## 4. 원본 식별과 해시 관리

패치 개발 초기에 대상 파일의 해시를 기록해두면 사고를 크게 줄일 수 있습니다.

추천:

```text
전체 패키지 확인용: MD5 또는 SHA-256
실제 패치 대상 파일: SHA-256
```

특히 최종 패처에서는 **패치 대상 파일 자체의 SHA-256**을 검사하는 방식이 좋습니다.

```text
사용자가 RomFS 선택
        ↓
대상 파일 존재 여부 확인
        ↓
원본 SHA-256 확인
        ↓
모두 일치할 때만 패치 시작
```

이렇게 하면 잘못된 버전이나 이미 수정된 RomFS에 패치를 적용하는 사고를 막을 수 있습니다.

> [!NOTE]
> 공개 기술 문서에는 해시를 꼭 넣을 필요는 없습니다. 특정 프로젝트의 버전 식별용 해시는 해당 프로젝트 저장소나 Release 문서에서 관리하고, 공용 아카이브에는 원리만 기록하는 편이 깔끔합니다.

## 5. RomFS 파일 인벤토리 만들기

다음 단계는 게임 내부에 어떤 자산이 있는지 파악하는 것입니다.

먼저 확장자·폴더·파일 크기를 기준으로 목록을 만듭니다.

예시 분류:

```text
script/        → 대사 / 이벤트 / 선택지
font/          → 폰트 / 글리프 / 문자 매핑
system/        → 메뉴 / 설정 / 공통 UI
movie/         → 영상 / 자막
image/texture/ → 타이틀 / 지도 / 버튼 / 옵션 이미지
sound/         → 음성 / 효과음
```

게임마다 이름과 포맷은 완전히 다르므로 폴더 이름만 보고 확정하지 말고 실제 파일을 검사해야 합니다.

### 처음 조사할 때 추천 산출물

```text
file-inventory.csv
format-notes.md
text-candidates.txt
font-notes.md
ui-assets.md
```

이 기록이 쌓이면 나중에 다른 게임에서도 조사 순서를 재사용할 수 있습니다.

## 6. 텍스트 포맷 찾기

대사와 UI 문자열은 게임마다 저장 방식이 다릅니다.

대표적인 경우:

```text
- 평문 UTF-8 / UTF-16
- Shift-JIS 계열
- 문자열 테이블
- 바이너리 스크립트
- 압축 컨테이너
- 포인터 기반 문자열
- 명령 코드 + 문자열이 섞인 스크립트
```

### 분석 순서

1. 일본어 문자열이 실제 파일에 존재하는지 검색
2. 문자열 앞뒤 바이트 패턴 확인
3. 문자열 길이 / 포인터 / 인덱스 구조 확인
4. 제어 코드와 텍스트를 분리
5. 추출 → 수정 → 재삽입이 가능한 도구 작성
6. 단일 문장 샘플로 실기 검증
7. 성공한 방식만 전체로 확장

### 제일 중요한 규칙

처음부터 수천 줄을 한 번에 바꾸지 않습니다.

```text
단일 샘플
  ↓
게임 실행 확인
  ↓
한글 표시 확인
  ↓
줄바꿈 / 선택지 / 이벤트 진행 확인
  ↓
전체 적용
```

이 방식이 디버깅 비용을 압도적으로 줄여줍니다.

---

## 7. 번역 원장과 빌드 데이터 분리

번역 작업은 원본 바이너리를 직접 편집하기보다 별도의 번역 원장을 두는 것이 좋습니다.

예:

```text
id | jp | ko | speaker | status | note
```

상태값 예시:

```text
draft
reviewed
approved
hold
```

빌드 프로그램은 이 원장을 읽어 게임 포맷으로 다시 삽입합니다.

장점:

- 번역 검수와 바이너리 작업 분리
- 오역 수정이 쉬움
- 재빌드 가능
- Git으로 변경 이력 관리 가능
- 캐릭터 말투 / 용어 통일이 쉬움

---

## 8. 제어 코드 보존

게임 스크립트에는 대사만 들어있는 것이 아닙니다.

예:

```text
- 화자 변경
- 줄바꿈
- 대기
- 음성 재생
- 표정 변경
- 분기
- 선택지
- 이벤트 호출
- 색상 / 강조
```

이런 값을 번역 과정에서 삭제하거나 순서를 바꾸면 게임이 깨질 수 있습니다.

따라서 추출 도구는 가능하면 다음 구조로 설계합니다.

```text
[제어 코드] + [번역 가능한 문자열] + [제어 코드]
```

번역자는 문자열만 수정하고, 빌더는 제어 코드를 원래 위치에 복원합니다.

## 9. 한글 폰트 문제 해결

일본어 게임은 한글 글리프를 포함하지 않는 경우가 많습니다.

이때 필요한 작업은 크게 두 종류입니다.

### 9-1. 기존 폰트에 한글 글리프 추가

```text
원본 폰트 분석
→ 사용 가능한 글리프 영역 확인
→ 한글 글리프 생성
→ 문자 코드 ↔ 글리프 인덱스 연결
→ 게임에서 출력 테스트
```

### 9-2. 문자 매핑 테이블 수정

게임이 자체 문자 테이블을 사용한다면 단순히 TTF/OTF 파일을 교체하는 것으로 끝나지 않습니다.

별도의 매핑 테이블이나 atlas 좌표를 수정해야 할 수 있습니다.

### 확인 항목

```text
- 한글 누락
- 초성/중성 깨짐
- 글자 폭
- 줄 높이
- 자간
- 작은 UI에서 잘림
- 강조 색상 / 그림자
```

---

## 10. UI 이미지 한글화

타이틀, 옵션, 지도, 버튼 등이 문자열이 아니라 **이미지 자체에 일본어가 박혀 있는 경우**가 많습니다.

이런 경우 텍스트 패치와 별도로 이미지 자산을 찾아야 합니다.

일반적인 흐름:

```text
압축 파일 발견
→ 압축 해제
→ 텍스처 / atlas 추출
→ 일본어 영역 위치 확인
→ 동일 크기·레이아웃으로 한국어 이미지 제작
→ 재삽입
→ 재압축
→ 게임에서 검증
```

### Atlas일 때 주의

한 장의 이미지에 여러 메뉴 조각이 들어있는 경우가 있습니다.

이 경우:

- 이미지 전체 크기 유지
- 각 요소 좌표 유지
- 투명도 유지
- UV가 참조하는 위치 변경 금지

처음에는 메뉴 하나만 바꾼 샘플을 만들어 실기 검증한 뒤 전체 atlas를 작업하는 것이 좋습니다.

---

## 11. 영상 자막 / 영상 파일

오프닝·엔딩 영상 안에 일본어 자막이 직접 들어있는 경우 영상 파일 자체를 수정해야 할 수 있습니다.

권장 작업 방식:

```text
원본 영상은 사용자가 자신의 게임에서 준비
→ 번역용 자막 제작
→ 동일한 재생 조건을 유지하도록 영상 제작
→ 수정 결과만 차이 패치로 배포
```

공용 저장소에는 다음을 올리지 않습니다.

```text
- 원본 영상
- 원본 음성
- 원본 스크린샷 대량 덤프
- 원작 자막 전체
```

기술 문서에는 **코덱, 해상도, 프레임레이트, 컨테이너 보존 원칙** 정도만 기록합니다.

---

## 12. 변경 파일만 모으기

한글화가 끝났다고 RomFS 전체를 배포하면 안 됩니다.

최종 빌드에서는 **실제로 변경된 파일만** 모읍니다.

예:

```text
work/original-romfs/
work/translated-romfs/
        ↓ compare
work/changed-files/
```

변경 파일 목록을 manifest로 만들어두면 매우 편합니다.

예:

```json
{
  "files": [
    "romfs/path/example1",
    "romfs/path/example2"
  ]
}
```

실제 프로젝트에서는 파일 이름과 게임 내부 데이터가 공개되기 민감한 경우 목록을 private 작업 폴더에서만 관리하고, 공개 문서에는 구조만 설명합니다.

## 13. xdelta / VCDIFF 방식으로 패치 만들기

원본 파일 전체를 배포하지 않고 **원본과 수정본의 차이**만 배포하는 방식이 유용합니다.

대표적인 도구가 `xdelta3`입니다.

개념:

```text
Original File
     +
Delta Patch
     ↓
Translated File
```

배포 ZIP에는 보통 다음 정도만 넣습니다.

```text
패처 실행 파일
patch/
  └─ *.xdelta
xdelta3 실행 파일 또는 라이브러리
오픈소스 라이선스
설명서
```

원본 게임 파일은 넣지 않습니다.

### 패처에서 권장하는 검증 순서

```text
1. 패처 자체 파일 확인
2. delta 파일 무결성 확인
3. 원본 파일 SHA-256 확인
4. 임시 폴더에 패치 적용
5. 결과 파일 SHA-256 확인
6. 모든 검사가 성공했을 때만 최종 결과 폴더 생성
```

원본 RomFS를 직접 덮어쓰지 않는 것이 중요합니다.

---

## 14. 패처는 원본을 수정하지 않는 구조가 좋다

좋은 패처 구조:

```text
사용자가 clean romfs 선택
        ↓
읽기 전용으로 원본 검사
        ↓
임시 작업 폴더 생성
        ↓
xdelta 적용
        ↓
결과 검증
        ↓
새 mod 폴더 생성
```

나쁜 구조:

```text
원본 RomFS를 바로 덮어쓰기
```

원본을 보존하면 패치 실패 시 복구가 쉽고, 사용자가 다른 모드와 비교하기도 편합니다.

---

## 15. Switch 실기용 출력 구조

Atmosphere의 LayeredFS 방식에서는 일반적으로 다음과 같은 구조를 사용합니다.

```text
SD카드/
└─ atmosphere/
   └─ contents/
      └─ <BASE_TITLE_ID>/
         └─ romfs/
            └─ (변경 파일)
```

중요:

> 모드 폴더는 일반적으로 **Base Title ID** 아래에 둡니다.

업데이트 Title ID를 `contents`의 상위 폴더로 잘못 사용하면 모드가 적용되지 않는 경우가 있습니다.

또한 아래와 같은 중복 폴더 실수가 자주 발생합니다.

```text
잘못된 예
<BASE_TITLE_ID>/romfs/romfs/...
<BASE_TITLE_ID>/<BASE_TITLE_ID>/romfs/...
```

최종 패키지를 만들 때 실제 SD 카드에 들어갈 구조를 그대로 만들어두면 사용자 실수가 줄어듭니다.

## 16. PC / Android 에뮬레이터용 출력 구조

같은 변경 파일이라도 플랫폼마다 요구하는 최상위 폴더 구조가 다를 수 있습니다.

따라서 패처가 결과를 두 종류로 자동 생성하게 만들면 편합니다.

예:

```text
Game-KR-PC/
└─ romfs/
   └─ ...

Game-KR-Switch-Android/
└─ <BASE_TITLE_ID>/
   └─ romfs/
      └─ ...
```

실제 게임 파일은 동일하고 설치를 위한 상위 폴더 구조만 다르게 만들 수 있습니다.

Android 11 이상에서는 `Android/data` 직접 접근이 제한될 수 있으므로, 에뮬레이터가 제공하는 **Add-ons / Mod 설치 기능**을 지원하는 구조도 함께 준비하는 편이 좋습니다.

## 18. 자주 터지는 문제

### 게임이 아예 실행되지 않음

가능한 원인:

```text
- 잘못된 파일 재압축
- 바이너리 크기 / 포인터 오류
- 손상된 자산
- 다른 버전 원본
```

### 일본어가 일부 남음

```text
- 문자열이 이미지 안에 존재
- 동일 문구가 여러 파일에 존재
- 런타임 생성 문자열
- 다른 언어 테이블 참조
```

### 글자가 깨짐

```text
- 한글 글리프 누락
- 문자 매핑 오류
- 폰트 atlas 좌표 오류
- 게임이 예상하지 못한 인코딩 사용
```

### 메뉴가 잘림

```text
- 일본어보다 한국어가 길어짐
- 고정 폭 UI
- 문자열 버퍼 제한
- 글리프 폭 문제
```

### 진행 불가 / 프리징

```text
- 제어 코드 손상
- 스크립트 포인터 오류
- 분기 ID 손상
- 잘못된 재압축
- 다른 버전의 파일 혼합
```

### 모드가 전혀 적용되지 않음

먼저 확인:

```text
- Base Title ID인가?
- romfs 폴더가 한 번만 있는가?
- 올바른 Update가 설치되어 있는가?
- 다른 모드가 같은 파일을 덮고 있지 않은가?
```

## 19. 한 번에 전체 작업하지 말고 Stage 방식으로 진행

대규모 한글화는 Stage를 나누는 것이 좋습니다.

예시:

```text
STAGE 1  RomFS / 파일 구조 조사
STAGE 2  텍스트 추출
STAGE 3  단일 한글 출력 샘플
STAGE 4  폰트 확정
STAGE 5  전체 대사 변환
STAGE 6  UI 이미지
STAGE 7  지도 / 옵션
STAGE 8  영상
STAGE 9  통합 빌드
STAGE 10 실기 검수
STAGE 11 패처 / 배포
```

각 Stage가 끝날 때 다음을 남깁니다.

```text
- 무엇을 확인했는지
- 어떤 파일을 수정했는지
- SHA / 해시
- 성공한 샘플
- 실패한 방법
- 다음 Stage 입력값
```

실패 기록도 매우 중요합니다. 같은 함정에 두 번 빠지는 것을 막아줍니다.

## 23. 추천 개발 철학

### 1) 원본 보존

항상 원본과 staging을 분리합니다.

### 2) 재현 가능한 빌드

수동 hex edit보다 스크립트로 다시 만들 수 있게 합니다.

### 3) 단일 샘플 우선

전체 적용 전에 한 항목으로 게임 실행까지 검증합니다.

"대충 같은 파일"이 아니라 정확히 지원하는 원본인지 검사합니다.

### 5) 변경 파일만 배포

원본 게임 데이터를 배포하지 않습니다.

### 6) 실기 기준

에뮬레이터만 보고 완료 판정을 내리지 않습니다.

### 7) 실패도 문서화

실패 원인과 재현 조건을 기록합니다.

## 24. 실제 배포 사례에서 확인된 좋은 구조

실제 Switch 한국어 패치 배포 사례를 분석하면 다음 구조가 매우 안정적입니다.

```text
배포 ZIP
├─ GUI 패처
├─ xdelta3
├─ patch/
│  └─ delta 파일
├─ 오픈소스 라이선스
└─ 설명서
```

패처 동작:

```text
clean merged RomFS 선택
→ 원본 검증
→ 임시 폴더에서 delta 적용
→ 결과 검증
→ PC용 / Switch·Android용 mod 구조 자동 생성
```

이 구조의 장점은 다음과 같습니다.

- 원본 파일을 직접 배포하지 않음
- 잘못된 게임 버전 차단 가능
- 원본 RomFS 훼손 방지
- 설치 구조 실수 감소
- PC / Switch / Android를 하나의 패치 소스로 관리 가능
- 결과 파일까지 해시 검증 가능
