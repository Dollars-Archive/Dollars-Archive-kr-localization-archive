# 최초 한글 출력·진행 안전성 사전검증

**게임 시작 후 실제로 표시되는 첫 문장부터 20번째 문장까지를 한 테스트 빌드에 묶습니다. 다양한 문자·길이·줄바꿈 조합을 미리 배치해 사용자가 한 번 순서대로 진행하면서 주요 출력·진행 위험을 함께 확인하도록 준비합니다.** 한글 표시만 보지 말고 각 문장을 넘긴 뒤 다음 대사로 정상 진행되는지도 확인합니다.

**첫 번째 문장은 짧은 한글 출력 샘플, 두 번째부터 20번째 문장은 다양한 테스트 조합으로 준비합니다.** 최초 한글 출력과 진행 안전성 확인은 하나의 단계이며, 첫 문장만 먼저 확인받고 나머지 시험을 위해 별도 빌드·승인을 다시 요구하지 않습니다.

이 문서는 최초 한글 출력 샘플을 만들 때 수행할 기술 합격 관문입니다. 대량 번역·일괄 정규화·전체 재삽입 이후로 미루지 않습니다. 1차 용어 선확정과 2·3·4차 최대 500논리행 검수의 작업량을 늘리는 단계가 아닙니다. **여러 번의 빌드·사용자 시험 요청으로 쪼개지 말고, 필요한 조합을 첫 20문장에 준비해 한 번의 통합 시험을 기본으로 합니다.**

**4단계의 첫 20문장은 사용자가 지정한 폰트 마스터를 처음부터 적용한 빌드로 시작합니다.** 임시 폰트로 먼저 확인한 뒤 두 번째 실행에서 지정 폰트로 바꾸는 2단계 인계는 하지 않습니다. 폰트 경로·마스터 문서 확인과 적용 방법은 아래 `지정 폰트 기준`을 따릅니다.

## 1. 적용 시점과 승인 범위

```text
워크플로 게이트와 폰트 마스터 README-ko.md·다른-게임-적용-설명서.md 확인
→ 원본·버전·기존 성공 자산 확인
→ 지정 폰트를 실제 적용한 첫 20문장 통합 시험 사본 준비와 왕복 재삽입 확인
→ 한 번의 진행으로 화면 한계·줄바꿈·문자 폭 조합·진행 확인
→ 게임별 출력/진행 규격과 허용 변환표 작성
→ 진행 가능 / 조건부 진행 / 기술 보강 후 재판정
→ 용어 기준자료도 준비된 범위에서 대량 번역·검수 시작
```

용어집·캐릭터·관계·말투 조사는 기술 시험과 병행할 수 있습니다. 다만 안전한 한글 출력·진행 경로가 입증되지 않은 채 대량 번역이나 전체 적용부터 밀어붙이지 않습니다. 조사용 소량 번역은 허용하되 최종 적용 승인과 구분합니다.

첫 20문장 시험을 설계하기 전에 이 문서 `workflow/EARLY-TEXT-RUNTIME-GATE.md`를 먼저 읽습니다. 게임별 작업에서는 폰트 마스터의 `README-ko.md`와 `다른-게임-적용-설명서.md`도 빌드 전에 확인합니다.

이 문서는 시험 기준이지 실제 파일 수정·에뮬레이터 조작·장시간 플레이의 별도 승인을 대신하지 않습니다. 프로젝트와 사용자가 허용한 범위에서만 실행합니다. 문서를 추가했다는 이유로 시험 완료를 선언하지 않습니다.

기존 프로젝트에는 이미 검증된 결과를 재사용하고 누락된 조건만 보강합니다. 폴더·원장·성공 패치를 다시 만들거나 기존 번역을 폐기하지 않습니다. 진행 불가 보고가 나오면 해당 변환·영향 범위의 신규 일괄 적용을 중단하고 마지막 정상본과 비교합니다.

## 2. 시험 기준선과 원본 보호

- 게임명, 플랫폼, 지역/언어, 판본·업데이트, 실제 대상 파일, 원본 해시, 빌더·인코딩·폰트·실행 환경을 기록합니다. 같은 시리즈의 다른 작품 결과를 자동 상속하지 않습니다.
- 원본 ROM/ISO·추출 원본·원문 필드·사용자 실플레이 확정값은 수정하지 않습니다. 시험은 별도 work/analysis/staging 사본과 백업한 시험용 세이브에서 합니다.
- 비교 기준은 원본 실행, 텍스트 무변경 추출→재삽입본, 가장 작은 정상 한글 샘플입니다. 재삽입만 해도 진행이 깨지면 줄바꿈이나 문자 폭 탓으로 단정하지 않습니다.
- 첫 20문장에 조건별 사례와 실제 사용할 조합을 구분해 배치합니다. 각 사례의 변경 조건을 짧게 적어 한 번의 시험에서도 어느 조건에서 문제가 났는지 찾을 수 있게 합니다. 실패하면 전체 시험을 반복하지 말고 관련 문장·조건만 기준선과 비교합니다. 여러 조건이 함께 달라진 사례는 원인이 분리됐다고 단정하지 않습니다.
- 화면 캡처만으로 진행 성공을 판정하지 않습니다. 행 ID/row_key, 장면·진입 방법, 실제 표시와 다음 대사·장면 도달 결과를 함께 남깁니다.

## 지정 폰트 기준 (4단계)

4단계의 첫 20문장 시험 빌드는 아래 지정 폰트 마스터를 **1~20번 전 문장에 처음부터 실제 적용한 상태**로 만듭니다. 임시 폰트로 측정하거나 먼저 배포한 뒤, 다음 실행에서 지정 폰트로 교체하는 방식은 이 계약의 이행이 아닙니다.

- 지정 폰트 마스터: `D:/Codex/한글화 프로젝트/# Font 모음/MaruBuri-SemiBold-HD-PPSSPP`
- 빌드 전에 마스터의 `README-ko.md`와 `다른-게임-적용-설명서.md`를 읽고 적용 순서·전제를 확인합니다. 마스터 원본은 읽기 전용으로 다룹니다.
- 마스터의 실제 소스는 `font/MaruBuri-SemiBold.otf`와, 누락 한글을 위해 선언된 `NotoSerifKR` 대체 manifest입니다. 임의의 다른 폰트로 조용히 바꾸지 않습니다.
- `full-hangul-master`의 13px/52px glyph/atlas profile은 참고 자료입니다. 13px·3줄과 PPSSPP 텍스처 해시는 다른 한 게임에서만 검증된 값이므로 모든 게임에 강제하지 않습니다. 대상 게임의 셀·크기·베이스라인·인코딩·엔진에 맞게 조정합니다.
- PPSSPP HD 텍스처는 대상 게임에서 실제로 덤프한 해시가 있어야 합니다. PPSSPP가 아닌 엔진은 PSP 텍스처를 그대로 복사하지 않고 해당 엔진용으로 변환한 glyph asset을 사용합니다.
- 시험 빌드에 폰트 소스 식별자와 해시, 적용 결과 profile(파일·크기·셀·베이스라인·자간·대체 폰트·엔진 형식)을 기록합니다.
- 폰트를 구할 수 없거나 대상 엔진과 호환되지 않으면 정확한 기술 차단 사유를 먼저 보고합니다. 무단 대체·변형으로 통과시키지 않고, 임시 폰트 빌드를 사용자 시험으로 넘기지 않습니다.
- 사용자가 명시적으로 선택한 폰트는 기존의 3개 후보 선정 규칙보다 우선합니다. 이후 사용자가 폰트 변경을 요청하면 영향받는 문장·조건만 재시험합니다.

## 3. 첫 20문장 한 번의 통합 시험

- 시작은 게임 초반의 **실제 첫 문장**이며 임의로 편한 장면의 20문장으로 대체하지 않습니다. 실제 표시 순서대로 1~20번과 원장 ID/row_key를 대응합니다. 제어 명령이나 CSV 행 수를 표시 문장 수로 세지 않습니다. 원래 문장이 여러 행에 나뉘었으면 표시 단위로 묶습니다. 각 표시 번호는 row_key/원문 위치, 실제 주입 문구, 변경 조건, 기대 표시, 다음 대사 전환까지 사례표에 적습니다.
- 첫 번째 문장은 짧은 한글로 기본 표시를 확인합니다. 두 번째부터 20번째 문장에는 보통·긴 한글, 받침과 복잡한 획, 숫자·영문·공백·문장부호, 혼합 문구, 줄 폭 경계와 여러 줄을 분산 배치합니다. 각 문장은 적용 가능한 시험 축을 하나 이상 맡고 같은 조건만 반복하지 않습니다. 시험 사본의 번역 필드에 실제로 주입하며, 원문 필드와 보호 명령은 보존하고 시험용 문구가 최종 번역에 섞이지 않게 구분합니다. 주입 없는 체크리스트만으로 인계하지 않습니다.
- 아래 표의 **해당 게임에서 실제로 쓸 조건을 20문장 안에서 최대한 함께 확인**합니다. 이미 확인된 허용 변환은 실제 조합으로 넣고, 미확정 줄바꿈·문자 폭 변경은 사례를 구분해 시험합니다. 불필요한 변환이나 임의의 초장문을 추가하지 않습니다. 바이트·버퍼 예산을 넘는 잘못된 입력은 먼저 정적 검사에서 차단합니다. 적용 가능한 축에는 모두 문장 번호를 배정하고, 미해당은 그 기능이 실제 20문장 범위에 없다는 구체적 근거를 적습니다.
- 이름·변수·음성·대기·선택지·특수 창은 그 20문장에 실제로 있는 경로만 확인합니다. 없는 기능을 억지로 삽입하거나 먼 장면까지 추가 플레이시키지 말고 `미해당 / 미확인`으로 짧게 표시합니다. 20문장 미만인 게임은 실제 범위만 사용합니다.
- 사용자에게는 테스트 빌드와 바로 실행하는 `.cmd`, **처음부터 20문장까지 순서대로 진행하는 한 번의 확인 요청**, 1~20 사례표를 함께 제공합니다. 문장별로 여러 차례 승인을 요구하지 않습니다. 20번째 문장 이후의 대사 전환까지 확인하고, 문제 발생 시 문장 번호·증상만 받습니다. 사용자 확인 전 런타임 결과는 `PENDING`이며 PASS로 기록하지 않습니다. 해당 범위에서 20번째 이후 전환에 도달할 수 없으면 강제 장면 점프 없이 limitation으로 남깁니다. 수정 후에는 실패한 조건과 영향받은 부분만 재확인합니다.
- 성공한 조건은 재사용합니다. 한 번의 시험에서 확인할 수 있는 위험을 최대한 모으는 것이 목표이며, 이를 전 게임·전 기능의 모든 결함이 없다는 보장으로 보고하지 않습니다. 결과는 `통과한 조건 / 실패한 조건 / 미확인`으로 짧게 정리합니다. 미확인 항목을 이유로 자동으로 시험 범위를 늘리지 않습니다.

**번역문 공백 기준:** 번역문 띄어쓰기는 기본적으로 반각 공백(U+0020)을 사용한다. 첫 20문장 테스트에도 반각 공백을 적용해 실제 폭·줄바꿈·다음 대사 진행을 함께 확인한다. 원문·제어 토큰·고정폭 정렬 등 보호 영역은 일괄 치환하지 않으며, 게임 구조상 전각 공백이 필요한 예외는 근거와 적용 범위를 기록한다.

### 20문장에 배치할 시험 축

| 시험 축 | 최소 확인 내용 | 합격 근거 |
|---|---|---|
| 가로 한계 | 실제 가로 픽셀 폭, 고정폭이면 셀 수, 한글 연속·숫자·영문·공백·혼합 문구의 표시 가능 글자 수 | 폰트·크기·자간·배율·대사창 종류·문구별 실측값과 잘림 경계 |
| 세로 한계 | 줄 높이, 최대 표시 줄 수, 마지막 줄·빈 줄·명시적 줄바꿈과 자동 줄바꿈 | 화면 하단 잘림·겹침·다음 페이지 처리와 진행 결과 |
| `[n]` | 원형 유지, 삭제, 위치 이동, 추가, 개수 변경을 각각 별도 시험 | 작업 종류별 표시·음성·대기·다음 대사·장면 진행 결과 |
| 자동 줄바꿈 | 명시적 `[n]`이 없는 한 줄·경계 부근·여러 줄 문구 | 자동 줄바꿈 유무, 실제 위치와 진행 안전성 |
| 반각·전각 | 실제 등장하는 영문·숫자·문장부호·공백·가나 등에서 한 종류씩 변경 | 변경 전후 코드 포인트/게임 인코딩 바이트, 화면과 진행 결과 |
| 길이·RSC | 이미 확인된 파일·레코드·문자열·버퍼 제한의 단위, 한계 이내/경계(알려진 바이트·버퍼 상한은 초과하지 않음) | 빌더 검증과 실제 증상. 화면 폭과 별도 기록 |
| 제어 구조 | 페이지·음성·대기·분기·변수·종료 명령, 레코드 경계·길이·정렬 | 파서/빌더 왕복 및 보호 필드 비교. 무단 수정 금지 |
| 긴 한글·치환 | 긴 어절, 숫자·영문 혼합, 확인된 범위의 이름/변수 치환 | 잘림·멈춤·오동작 없이 다음 대사와 다음 장면에 도달 |

가변폭에서는 글자 수 하나를 보편적인 최대값으로 만들지 않습니다. 사용자에게는 **한 줄에 몇 글자 정도가 안전한지와 최대 몇 줄인지**를 보여주되, 전제인 문구·폰트·폭을 함께 기록합니다. 정확한 상한을 확정하지 못하면 '검증된 안전범위'와 '진짜 상한 미확정'을 구분합니다. 다른 게임의 38칸×2줄 같은 값을 기본값으로 가져오지 않습니다.

지정 폰트가 있으면 그 폰트를 첫 시험부터 사용하며, 3개 후보를 먼저 비교해야 한다는 기존 규칙은 적용하지 않습니다. 사용자가 명시적으로 선택한 폰트가 우선합니다. 폰트·크기·자간·빌더가 바뀌면 영향받은 조건만 재검증하고, 다른 게임의 13px/3줄·PPSSPP 텍스처 해시를 기본값으로 상속하지 않습니다. Pretendard Bold를 모든 작품에 강제하지 않습니다.

경계 시험은 복구 가능한 사본에서 작은 증가로 수행합니다. 무의미한 초장문·대량 덤프·장시간 자동 플레이는 기본 시험이 아닙니다. 명백한 멈춤이 발생하면 무작정 반복하지 말고 기준선 복원과 해당 조건의 원인 조사로 전환합니다.

### 사용자 인계 전 관문

첫 20문장 설계 전에 이 문서를 읽고, 아래 사례표를 실제 주입 결과로 채운 뒤 빌드합니다. 표와 산출물이 다르거나 주입되지 않은 항목이 있으면 인계하지 않습니다.

| 표시 번호 | row_key/원문 위치 | 실제 주입 문구 | 변경 조건 | 기대 표시 | 다음 대사 전환 |
|---|---|---|---|---|---|
| 1 | 실제 첫 표시 행 | 짧은 한글 | 지정 폰트·기본 조건 | 1줄 정상, 잘림 없음 | 2번 대사 표시 |
| 2~19 | 각 행의 원문 위치 | 실제 주입 문구 | 축별 변경 조건 | 예상 줄 수·폭·문자 | 다음 번호 대사 표시 |
| 20 | 실제 20번째 표시 행 | 실제 주입 문구 | 마지막 축 조건 | 예상 줄 수·폭·문자 | 20번 이후 첫 전환 |

`변경 조건`에는 해당 문장이 맡은 축과 실제 변경(예: `[n]` 삭제, 전각 공백, 경계 길이)을 적고, `기대 표시`에는 줄 수·가로 한계·문자 종류를 적습니다. 표의 2~19는 실제 문장별 행으로 펼쳐 작성하며, 같은 조건의 반복으로 빈 축을 채우지 않습니다.

| 시험 축 | 배정 문장 | 적용/미해당 근거 |
|---|---|---|
| 가로 한계 | 실제 번호 | 실제 픽셀 폭/셀 수와 잘림 경계 |
| 세로·최대 줄 | 실제 번호 | 줄 높이·마지막 줄·다음 페이지 |
| 자동 줄바꿈 | 실제 번호 | 명시 `[n]` 없는 경계 문구 |
| 명시적 줄바꿈 | 실제 번호 | `[n]` 외 실제 개행·페이지와 표시·진행 |
| `[n]` preserve/remove/move/add/count_change | 동작별 실제 번호 | 동작별 표시·진행 결과를 분리 |
| 반각·전각 | 실제 번호 | 실제 등장 문자 종류별 변경 |
| 한글·영문·숫자·공백·문장부호 | 실제 번호 | 각 문자군 최소 1개 |
| 긴 한글·변수 치환 | 실제 번호 | 실제 사용 범위의 긴 어절·치환 |
| 인코딩·버퍼·제어 구조 | 실제 번호 | 빌더·보호 필드·예산 검사와 연결 |

`배정 문장`은 실제 표시 번호(예: `2, 7, 11`)로 채웁니다. `1~20 중` 같은 범위 표기만 남기면 미완료입니다. 미해당 축은 "없음"만 쓰지 않고, 해당 20문장에 그 기능·문자·경로가 실제로 없다는 근거를 한 줄로 적습니다. 새 기능을 억지로 넣어 축을 채우지 않습니다.

**인계 GO — 아래를 모두 충족할 때만 사용자에게 넘깁니다.**
- 지정 폰트가 산출물에 실제 적용되고, 소스 식별자/해시와 결과 profile이 기록됨
- 1~20이 실제로 주입되었고, 사례표의 문구·조건·다음 전환과 산출물이 일치함
- 소스→최종 텍스트 대응, glyph coverage, 보호 필드, 바이트·버퍼 예산의 정적 검사와 정적 빌드가 끝남
- 적용 가능한 모든 축에 문장 번호가 있고, 미해당은 구체적 근거가 있음
- 테스트 빌드 1개, 실행 `.cmd`, 1~20 사례표, 차단·한계 요약이 준비됨
- 런타임 결과는 사용자 확인 전까지 `PENDING`으로 기록됨

**인계 NO-GO — 하나라도 해당하면 보류하고 원인을 먼저 해결합니다.**
- 임시 폰트 선행 측정 또는 지정 폰트로 바꾸는 두 번째 사용자 실행을 전제로 함
- 체크리스트만 있고 실제 주입이 없거나, 표와 빌드의 문구·폰트가 다름
- 적용 가능한 축의 문장 배정 누락, 근거 없는 미해당 처리, 무리한 초장문 주입
- 폰트 출처·해시 불명, 다른 게임 검증값 강제, 보호 필드 훼손 또는 알려진 예산 초과
- 사용자 확인 없이 런타임 PASS를 기록하거나, 도달 불가 전환을 강제 점프로 대체함

GO는 이 20문장 범위의 인계 조건이며 전 게임·전 기능의 무결성 보장이 아닙니다. 기록은 기존 progress/layout_profile에 1~20 사례표와 `PENDING` 상태를 추가하는 정도로 끝내며, 새 검사 프로그램이나 별도 대형 QA를 만들지 않습니다.

## 4. `[n]`은 동작별로 허가한다

`[n]`이 화면 줄바꿈처럼 보인다는 사실은 삭제·이동·추가가 안전하다는 증거가 아닙니다. 파서의 명령 분류와 실제 진행 시험을 함께 확인합니다.

게임별·대사창별·적용 구간별로 다음을 각각 `PASS / FAIL / UNTESTED`로 기록합니다.

- `preserve`: 기존 배치 유지
- `remove`: 삭제
- `move`: 개수 유지 상태의 위치 이동
- `add`: 추가
- `count_change`: 개수 증감

한 동작의 성공을 다른 동작의 허가로 확대하지 않습니다. 자동 줄바꿈 성공도 `[n]` 삭제 후 진행 성공을 대신하지 않습니다. 필요한 동작별 사례와 실제 사용할 조합은 첫 20문장의 같은 빌드에 배치해 함께 확인하며, 이미 확인된 조합을 별도 시험으로 반복하지 않습니다.

**삭제·이동으로 진행이 멈춘 작품에서는 해당 변환을 금지합니다.** 정상 기준선의 토큰 값·개수·순서·구간 경계 등 검증된 불변조건을 유지하고, 허용 구간 안에서 한국어 문장을 다듬습니다. 보호 명령을 넘겨 문장을 이동하거나 후행 `[n]` 붙이기·페이지 명령 추가를 범용 우회책으로 사용하지 않습니다.

원문 필드의 `[n]` 위치는 그대로 보존합니다. 번역 필드에서 허용된 동작만 적용하며, CSV 행 구분·셀 내부 실제 개행·`[n]` 문자 토큰을 혼동하지 않습니다. 미검증은 허용이 아니라 보존/보류입니다.

## 5. 반각·전각과 보이지 않는 문자도 진행 규격에 포함한다

반각·전각 변경을 단순한 미관 정리로 취급하지 않습니다. 다음은 시험 후보의 예시이지 모든 게임에서 바꿀 수 있다는 뜻이 아닙니다.

```text
A / Ａ
1 / １
! / ！
? / ？
반각 공백 U+0020 / 전각 공백 U+3000
실제 등장하는 반각·전각 가나와 문장부호
```

- 게임에 실제로 있는 문자 종류를 한 번에 하나씩 시험합니다. 공백·문장부호와 제어 토큰 내부 문자를 구분합니다.
- 추출 원문 → 편집/검수 CSV → 빌더 입력 → 인코딩된 출력의 각 단계에서 값이 어디서 달라지는지 비교합니다. 화면상 비슷한 글자만 비교하고 끝내지 않습니다.
- 문자열 폭, Unicode 코드 포인트, 게임 인코딩 바이트 수, 레코드 길이·종료·정렬을 따로 확인합니다. 반각/전각이 곧 고정된 1바이트/2바이트라는 가정을 하지 않습니다.
- 전각↔반각 일괄 변환, NFKC/NFKD 같은 호환 정규화, 공백 trim·연속 공백 축약, 문장부호 자동 교정은 안전성이 입증되기 전에는 금지합니다. NFC 등 다른 자동 정규화도 게임에 필요한지와 허용 범위를 먼저 검증합니다.
- 실패한 문자 종류·구간의 불변조건을 등록하고 번역·검수 지시문과 CSV 반입기·빌더에 전달합니다. '일반 한국어 표기상 더 자연스럽다'는 이유로 위반하지 않습니다.
- 이 규칙은 일본어 본문을 한글로 번역하지 말라는 뜻이 아닙니다. 번역 가능한 본문과 폭/바이트/명령에 민감한 보호 부분을 구분하고, 검증된 한글 매핑·인코딩 경로를 사용합니다.

문자 폭 변경과 진행 이상이 함께 관측돼도 원인이 폭 자체인지, 인코딩·길이 계산·폰트 매핑·명령 파싱·종료 처리인지 구분합니다. 확인 전에는 원인을 확정하지 않습니다.

## 6. '표시 성공'과 '진행 성공'을 분리한다

각 대표 샘플은 텍스트를 표시한 상태에서 끝내지 않고 다음을 확인합니다.

1. 문자가 정상 출력되고 폭·줄 수 조건을 만족하는가?
2. 대사 종료 후 다음 대사로 넘어가는가?
3. 장면의 마지막 대사·선택지를 지나 실제 다음 장면으로 넘어가는가?
4. 해당 장면에 음성·대기·연출·분기가 있으면 기준선과 동작이 같은가?

작품에서 지원하고 실제 사용할 일반 진행·자동 진행·스킵 경로가 다르면 대표 사례를 구분합니다. 필요한 경우 시험용 세이브의 저장·재로드도 확인하되 미실행 기능은 PASS로 표시하지 않습니다.

픽셀 측정 PASS, 구조/RSC PASS, 진행 PASS는 서로를 대신하지 않습니다. 한 장면 성공을 전체 대사·전 플랫폼·전 판본 성공으로 확대하지 않습니다.

## 7. 착수 판정

| 판정 | 조건 | 허용되는 후속 작업 |
|---|---|---|
| 진행 가능 | 정적 인계 관문을 통과하고, 사용자 1회 순차 확인에서 1~20 표시·다음 대사·20번 이후 전환이 확인됨. 적용 범위가 명확함 | 확인한 조건 안에서 번역·검수·샘플 확대 |
| 조건부 진행 | 예: `[n]`과 문자 폭 조건을 보존하면 정상이나 삭제·정규화는 실패 또는 미검증 | 검증된 보수적 경로만 허용. 제한·영향을 사용자에게 알리고 금지 변환을 반입 단계에서 차단 |
| 기술 보강 후 재판정 | 보수적인 한글 샘플도 진행 불가하거나 안전 경로를 입증할 근거가 부족함 | 해당 범위 대량 번역/적용 보류. 파서·빌더·인코딩 등을 조사하고 재시험 |

`[n]` 삭제 실패 하나로 작품 전체를 '한글화 불가능'으로 결론 내리지 않습니다. 반대로 번역문이 한 번 보였다고 제작 가능성이 충분히 검증됐다고 하지 않습니다. 사용자에게 현재 방식의 가능성·제약·미해결 위험을 먼저 설명합니다.

## 8. 출력 규격·Drive 전달 계약

결과는 게임별 `layout_profile` 또는 기존 동등 자료에 통합합니다. 별도 JSON/문서를 쓸 수 있지만 기존 대사 CSV 스키마를 승인 없이 바꾸지 않습니다.

반드시 남길 내용:

- 게임·플랫폼·버전·실행 환경·빌더·폰트 식별값
- 지정 폰트 소스 식별자·해시, 원본 읽기 전용 여부, 적용 결과 profile(파일·크기·셀·베이스라인·자간·대체 폰트·엔진 형식)
- 1~20 표시 번호별 row_key/원문 위치, 실제 주입 문구, 변경 조건, 기대 표시, 다음 대사 전환과 런타임 상태 `PENDING / PASS / FAIL`
- 대사창/문자열 종류별 픽셀 한계, 최대 줄 수, 조건부 글자 수와 검증된 안전범위
- 자동 줄바꿈의 관측값
- `[n]` 동작별 `PASS / FAIL / UNTESTED`, 보호 명령·구간
- 반각/전각·공백·문장부호 보존 규칙과 허용 변환 목록
- RSC/인코딩/레코드 제한의 단위·한계·검사 방법 또는 미확정 상태
- 시험 전후 문구·토큰/바이트 diff, 행 ID, 장면 재현 방법, 표시·진행 결과
- 사용자 보고 / 직접 재현 / 코드 근거 / 추정의 구분, 규격 버전과 승인 범위
- 착수 판정 및 미해결 목록

이 규격은 용어집·캐릭터·관계·말투와 함께 작업 자료에 연결합니다. 규격 부재를 기본 허용으로 처리하지 않습니다. 초안의 격리 반입은 가능하지만 금지·미검증 변환을 최종 승인/배포에 자동 포함하지 않습니다. 이 문서를 이유로 별도 검수 프로그램 제작을 요구하지 않습니다. 기존 도구와 확인된 결과를 재사용하고 실제 수행 여부를 기록합니다.

Google Drive 작업 묶음을 만들거나 갱신할 때도 공통 기준 폴더에 이 게임의 출력/진행 규격과 버전을 넣고, 각 차수 지시문에는 해당 역할만 명시합니다.

## 9. 사용자 보고 사례와 미확정 범위

2026-09-13 정책 보강의 계기는 다음 사용자 보고입니다.

- 티어즈 투 티아라: `[n]` 변경 뒤 다음 장면 진행 불가. 반각/전각 변경 때도 진행 불가 보고.
- EVE 시리즈: 반각/전각 변경과 관련한 진행 문제를 겪었다는 보고.

이 문서 작성에서 해당 게임을 직접 재현한 것은 아닙니다. 정확한 판본·장면·변경 바이트·원인은 게임별 조사에서 확인해야 합니다. 이 사례를 근거로 Lotus 등 다른 작품의 `[n]` 의미나 제한값을 덮어쓰지 않습니다.
