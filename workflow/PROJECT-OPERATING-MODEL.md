# 게임 한글화 프로젝트 운영 모델

## 1. 한글화 프로젝트 상위 루트

모든 게임 한글화 작품은 기본적으로 다음 상위 루트 아래에 모아 관리합니다.

```text
D:\Codex\한글화 프로젝트
```

게임 하나당 이 상위 루트 바로 아래에 독립된 작품 폴더 하나를 둡니다.

```text
D:\Codex\한글화 프로젝트\<작품 폴더명>
```

명시적인 사용자 지시가 없는 한 새 한글화 프로젝트를 이 상위 루트 밖에 임의로 만들지 않습니다.
다른 작품 폴더는 형제 프로젝트이며, 현재 작업 범위로 지정되지 않은 다른 작품 폴더를 임의로 수정하지 않습니다.

## 2. 기준 프로젝트와 기본 디렉터리 구조

새 작품의 기본 폴더 구성은 다음 실제 프로젝트를 기준으로 합니다.

```text
D:\Codex\한글화 프로젝트\이상한 환상향 로터스 Lotus Labyrinth
```

확인된 최상위 기본 구조는 다음과 같습니다.

```text
<작품 폴더>/
├─ .github/
├─ docs/
├─ source/
├─ staging/
├─ tests/
├─ tools/
├─ work/
├─ .gitignore
└─ AGENTS.md
```

기본 용도:

- `.github/`: GitHub 메타데이터와 저장소 운영 파일
- `docs/`: 프로젝트 문서, 사용법, 설계 및 검증 기록
- `source/`: 실제 한글화 작업의 입력이 되는 게임별 소스/추출 자산 영역
- `staging/`: 전체 반영 전 중간 빌드·적용·검증 산출물
- `tests/`: 자동 테스트와 회귀 검증
- `tools/`: 추출기, 빌더, 패처, 변환기, 검증 도구
- `work/`: 조사, 분석, 실험, 로그, 임시 증거와 진행 중 작업
- `.gitignore`: 저장소에 포함하면 안 되는 원본·대용량·임시 산출물 관리
- `AGENTS.md`: 해당 작품에만 적용되는 작업 범위, 금지사항, 성공 자산, 검증 조건

폴더 이름만 보고 기준 프로젝트의 세부 파일 배치나 의미를 추측해서 복제하지 않습니다.
새 작품을 실제로 초기화하거나 구조를 크게 정비할 때는 가능한 실행 환경에서 기준 프로젝트를 직접 열어 현재 구조와 파일 역할을 확인한 뒤 범용 뼈대만 재사용합니다.

게임 전용 데이터, 코드, 번역, 로그, 오프셋, 원본 자산은 기준 프로젝트에서 새 작품으로 복사하지 않습니다.

### PS3 이하 작품의 `05_HD Pack`

PS3 및 그보다 이전 세대 게임은 작품 폴더에 다음 폴더를 기본으로 만들어 둘 수 있습니다.

```text
<작품 폴더>/05_HD Pack/
```

이 폴더는 향후 HD 텍스처/이미지 팩 제작을 위한 전용 작업 공간입니다.

**중요: `05_HD Pack` 폴더가 존재한다는 이유만으로 HD Pack 제작을 자동 시작하지 않습니다.**

- 기본 프로젝트 초기화 시에는 폴더만 준비합니다.
- 사용자가 "HD Pack 제작", "HD팩 작업", "텍스처 업스케일" 등으로 명시적으로 요청한 경우에만 실제 작업을 시작합니다.
- 한글화 작업을 지시받았다는 이유만으로 텍스처 덤프, 업스케일, 이미지 재가공, 대량 변환을 임의로 수행하지 않습니다.
- HD Pack 작업이 승인된 뒤에도 원본 자산 보존, 교체 규칙, 파일명/해시 매핑, 에뮬레이터 또는 실기 검증을 별도 작업축으로 관리합니다.
- HD Pack 결과는 번역/패치 결과와 섞어 자동 배포하지 않습니다. 사용자가 지정한 배포 범위에 따릅니다.

사용자가 HD Pack 제작 또는 가능성 분석을 명시적으로 요청한 경우에는 본격 작업 전에 반드시 `workflow/HD-PACK-PIPELINE.md`를 읽습니다.

HD Pack의 기본 전략은 **플레이 덤프 우선이 아니라 ROM/ISO 내부 자산 우선**입니다.

```text
ROM/ISO 내부에서 추출 가능한 2D 자산 확보
→ 소량 샘플로 구조와 매핑 검증
→ 기본 베이스 자산 HD화
→ 에뮬레이터 texture dump/hash와 자동·반자동 매칭
→ 이후 실제 플레이에서 기존 베이스에 없는 신규 dump만 증분 처리
```

즉 게임을 처음부터 끝까지 플레이하며 모든 텍스처를 처음부터 수집하는 방식을 기본값으로 삼지 않습니다.

PS2에서는 PCSX2 Texture Replacement를 대표 예로 사용하지만, 다른 구형 콘솔도 같은 원칙을 적용하고 실제 에뮬레이터의 덤프/교체 규칙은 해당 플랫폼에서 직접 확인합니다.

PS4 이후 또는 HD Pack이 필요하지 않은 플랫폼은 사용자가 별도로 요청하지 않는 한 이 폴더를 필수로 만들 필요가 없습니다.

### 한글화 폰트 후보 선정

게임에서 새 한글 폰트를 선택하거나 기존 폰트를 교체해야 하면 `workflow/FONT-SELECTION-POLICY.md`를 먼저 읽습니다.

기본 후보 검색처:

```text
https://font.emulog.app/#fonts
```

작품마다 실제 글리프 셀/타일 크기, BPP, 고정폭/가변폭, 글리프 수, 인코딩, 아틀라스 구조와 표시 픽셀 크기가 다르므로 폰트 이름이나 외형만 보고 바로 적용하지 않습니다.

기본 절차:

```text
게임의 실제 폰트 규격 조사
→ Font Share에서 기술적으로 맞는 후보 약 3개 선정
→ 같은 문구·같은 크기·같은 화면 조건으로 샘플 제작
→ 후보별 장단점과 함께 사용자에게 비교 제시
→ 사용자가 직접 최종 폰트 선택
→ 선택 결과를 프로젝트 확정값으로 기록
```

기술적으로 유효한 후보가 3개 미만이면 억지로 수를 채우지 않습니다.
사용자 선택 전에는 전체 폰트 교체나 대량 반영을 하지 않습니다.
사용자가 확정한 폰트는 이후 AI가 취향 판단만으로 임의 변경하지 않습니다.

### 번역 전 0단계: 용어집·캐릭터·관계 기준 선세팅

대량 대사 번역 또는 게임별 검수 프로그램의 본 번역 기준자료 등록 전에 반드시 `review/PRE-TRANSLATION-SETUP.md`를 읽고 0단계 기준자료를 준비합니다.

**핵심 등장인물과 빈출 용어가 비어 있는 상태에서 번역량부터 밀어붙이지 않습니다.**

최소 준비 대상:

- 캐릭터명·별칭·칭호
- 아이템·던전·시스템·스펠·기술·세계관 핵심 용어
- 캐릭터 성격·기본 말투·1인칭·말버릇
- 화자 → 청자 방향 관계도
- 반말/존댓말 기준
- 호칭 기준
- 근거 출처와 `confirmed / provisional / HOLD` 상태

캐릭터 이름은 사용자 확정값과 공식 자료를 먼저 사용합니다. 공식 자료가 일본어뿐이라 한국어 표기가 애매하면 나무위키의 통용 표기를 참고하고, 그것도 불충분하면 일본 위키·팬 위키·사전·작품 자료를 교차 확인합니다. 끝까지 애매하면 임의 확정하지 않고 HOLD합니다.

캐릭터 성격과 말투는 공식 소개, 실제 게임 일본어 대사, 매뉴얼·설정집·당시 연재 기사·인터뷰·특집 자료를 우선 조사합니다. 오래된 작품은 나무위키와 일본 위키의 정리도 보조 자료로 적극 활용하되 실제 일본어 원문·공식 자료와 충돌하면 후자가 우선합니다.

일본어판과 영어판이 모두 있으면 **용어와 대사 번역의 기준은 일본어 원문**입니다. 영어판은 의미·문맥·철자 확인용 보조자료로만 사용하며, 영어판의 추가·축약·순화·과장을 일본어보다 우선하지 않습니다.

검수 기본 단위는 다음과 같이 고정합니다.

```text
0단계: 기준자료·용어집 구축
→ 1차: 전체 대사집을 1,000행 단위로 기초 검수
→ 2차: 1차 결과 전체를 다시 1,000행 단위로 자연화·말투 검수
→ 3차: 2차 결과 전체를 다시 500행 단위로 최종 정밀검수
```

각 차수는 서로 다른 행 구간을 맡는 것이 아니라 **전체 대사집을 다시 훑는 별도 패스**입니다. 마지막 잔여 블록을 제외하면 기본 묶음 크기 1,000 / 1,000 / 500을 유지합니다.

## 3. 프로젝트 기본 단위

한 게임은 하나의 독립된 한글화 도메인으로 관리합니다.

```text
게임 1개
  → D:\Codex\한글화 프로젝트 아래 작품 폴더 1개
  → Codex 한글화 프로젝트 1개
  → 게임 전용 검수 프로그램 1개
  → 게임 전용 Google Drive 검수 작업공간 1개
```

다른 게임에서 성공한 코드나 분석법은 참고할 수 있지만, 게임별 데이터와 판정 규칙은 자동으로 섞지 않습니다.

## 4. Codex와 작업자 계층의 역할 분리

한글화 엔지니어링은 한 모델이 전부 직접 수행하는 구조가 아니라 **감독관 → 전문 실무 책임자 → 단순 작업자 → 외부 전문가** 구조로 운영합니다.

### GPT-5.6 Sol High: 소장 / 감독관

Sol High는 프로젝트 전체를 파악하고 다음을 담당합니다.

- 사용자 요구와 성공 조건 해석
- 작업 분해
- 위험도·난이도 판단
- 작업자 배차
- 결과 비교와 충돌 해결
- 실제 diff·테스트·런타임 근거 검증
- 최종 통합

Sol이 직접 할 수 있다는 이유만으로 일반 실무를 혼자 수행하지 않습니다.

### DevSpace + Web GPT-5.6 Sol XHIGH: 분야별 과장 / 기본 전문 실무 책임자

일반~상당 난도의 실제 한글화 엔지니어링 실무를 기본적으로 담당합니다.

- 게임 파일/자산 분석
- 텍스트/자산 추출·재삽입 경로 조사
- 폰트/UI/영상/바이너리의 일반 구현 작업
- 빌더·패처·검수 도구 구현과 검토
- 중간~상당 난도 디버깅
- 여러 파일을 묶은 기술 조사와 설계 검토

전문 실무에 Web Sol XHIGH를 사용할 때는 DevSpace `open_workspace`를 실제 호출해 프로젝트 연결 상태를 확인합니다.

### GPT-5.6 Luna XHIGH: 기사 / 저위험 단순 작업자

- 파일·문자열 위치 조사
- 목록화와 반복 검색
- CSV/JSON/Markdown 정리
- 확정 규칙에 따른 일괄 처리
- 테스트 반복
- 해시·크기·개수 비교
- 로그 집계

새 설계 판단, 애매한 바이너리 추론, 어려운 원인 분석, 근거가 갈리는 번역·관계·존대 판정은 맡기지 않습니다.

### GPT-6 Astra Medium: 외주 전문업체

내부 실무진에게 맡기기 어려운 고난도 구현·디버깅을 담당합니다. 처음부터 명백히 Astra급 문제라면 하위 작업자를 일부러 실패시키지 않습니다.

### DevSpace + Web GPT-6 Pro: 최고급 외부 전문가

Astra급 접근으로도 풀리지 않거나 최고 수준 추론이 필요한 난제를 담당합니다.

### 웹 ChatGPT + Google Drive 언어 검수

Google Drive의 게임별 CSV와 기준 자료를 사용해 대량 번역/검수를 수행합니다.

- 0단계: 용어집·캐릭터·관계·말투 기준자료 조사와 보강
- 1차: 전체 대사집을 1,000행 단위로 기초 검수
- 2차: 1차 결과 전체를 다시 1,000행 단위로 자연화와 캐릭터 말투 보정
- 3차: 2차 결과 전체를 다시 500행 단위로 가장 엄격한 최종 정밀검수

Codex가 대량 대사 번역을 대신 수행하는 것을 기본 흐름으로 삼지 않습니다.

## 5. 공통 코드 재사용과 게임 데이터 격리

재사용 가능:

- 범용 CSV 파서
- 해시 검증기
- diff/manifest 생성기
- 공통 UI 컴포넌트
- 테스트 헬퍼
- 형식이 실제로 같다고 검증된 추출/빌드 코드

자동 재사용 금지:

- 용어집
- 캐릭터 정보
- 관계도
- 반말/존댓말
- 말투 규칙
- 런타임 오프셋
- 파일 포맷 가정
- 승인 번역
- 승인된 작품별 폰트 선택값
- 플레이 검수 결론
- 다른 게임의 HD Pack 원본/업스케일 결과/교체 매핑

같은 시리즈, 같은 엔진, 비슷한 파일명이라는 이유만으로 호환성을 확정하지 않습니다.

## 6. 프로젝트 `AGENTS.md` 우선

대상 프로젝트에 `AGENTS.md`가 있으면 아카이브의 일반 지침보다 해당 프로젝트 규칙을 우선합니다.

`AGENTS.md`에는 최소한 다음을 둡니다.

- 정확한 게임/프로젝트 범위
- 수정 허용 루트
- 건드리면 안 되는 다른 프로젝트
- 지원 버전과 기준 원본
- 이미 승인된 자산과 번역
- 번역 전 기준자료 준비 상태
- 승인된 폰트와 폰트 규격
- 테스트/실기 검증 조건
- 모델 위임 규칙
- 실패 기록 방식
- PS3 이하 작품이라면 `05_HD Pack`의 사용 여부와 현재 승인 상태

## 7. Stage 방식

큰 작업은 한 번에 전체 적용하지 않습니다.

기본 흐름:

```text
조사
→ 단일 샘플
→ 런타임 검증
→ 전체 적용
→ 자동 검증
→ 변경분만 배포
```

각 Stage 종료 시 다음을 기록합니다.

- 확인된 사실
- 수정 파일
- 해시/크기 등 검증값
- 성공 샘플
- 실패한 접근
- 다음 단계 입력값

## 8. 성공/실패 기록

실패 기록은 폐기물이 아니라 다음 작업의 입력입니다.

기록할 것:

- 어떤 방법을 시도했는지
- 어떤 결과가 나왔는지
- 정적 검증과 실제 런타임 결과가 어떻게 달랐는지
- 재현 조건
- 롤백 기준

다만 게임 전용 실패 기록을 범용 아카이브에 올릴 때는 저작권 자료, 개인 경로, 비공개 데이터 등을 제거하고 재사용 가능한 원리만 남깁니다.

## 9. 실제 프로젝트 파일이 최우선 근거

아카이브는 참고서입니다. 실제 프로젝트의 파일과 실행 결과를 대신하지 않습니다.

따라서 Codex는 항상 다음 순서를 지킵니다.

1. 대상 프로젝트 실제 조사
2. 기존 성공 코드와 승인 산출물 확인
3. 관련 아카이브 노하우 선택
4. 단일 샘플 적용
5. 런타임 검증
6. 성공 근거가 있을 때만 확장
