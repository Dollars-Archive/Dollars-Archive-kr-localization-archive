# 게임 한글화 프로젝트 운영 모델

## 1. 프로젝트 기본 단위

한 게임은 하나의 독립된 한글화 도메인으로 관리합니다.

```text
게임 1개
  → Codex 한글화 프로젝트 1개
  → 게임 전용 검수 프로그램 1개
  → 게임 전용 Google Drive 검수 작업공간 1개
```

다른 게임에서 성공한 코드나 분석법은 참고할 수 있지만, 게임별 데이터와 판정 규칙은 자동으로 섞지 않습니다.

## 2. Codex와 웹 ChatGPT의 역할 분리

### Codex

Codex는 한글화 엔지니어링을 담당합니다.

- 대상 게임 버전과 파일 구조 조사
- 텍스트/자산 추출 및 재삽입 도구
- 폰트, UI, 영상, 바이너리 패치
- 빌더, 패처, 검증 도구
- 테스트와 자동 검증
- 게임별 검수 프로그램
- staging/build/release 생성
- 최종 검수 CSV를 프로젝트에 반입

### 웹 ChatGPT

웹 ChatGPT는 Google Drive의 게임별 CSV와 기준 자료를 사용해 대량 번역/검수를 수행합니다.

- 1차 기초 검수
- 2차 자연화와 캐릭터 말투 보정
- 3차 최종 정밀 검수

Codex가 대량 대사 번역을 대신 수행하는 것을 기본 흐름으로 삼지 않습니다.

## 3. 공통 코드 재사용과 게임 데이터 격리

재사용 가능:

- 범용 CSV 파서
- 해시 검증기
- diff/manifest 생성기
- 공통 UI 컴포넌트
- 테스트 헬퍼
- 형식이 실제로 같다고 검증된 추출/빌드 코드

자동 재사용 금지:

- 용어집
- 캐릭터 정보
- 관계도
- 반말/존댓말
- 말투 규칙
- 런타임 오프셋
- 파일 포맷 가정
- 승인 번역
- 플레이 검수 결론

같은 시리즈, 같은 엔진, 비슷한 파일명이라는 이유만으로 호환성을 확정하지 않습니다.

## 4. 프로젝트 `AGENTS.md` 우선

대상 프로젝트에 `AGENTS.md`가 있으면 아카이브의 일반 지침보다 해당 프로젝트 규칙을 우선합니다.

`AGENTS.md`에는 최소한 다음을 둡니다.

- 정확한 게임/프로젝트 범위
- 수정 허용 루트
- 건드리면 안 되는 다른 프로젝트
- 지원 버전과 기준 원본
- 이미 승인된 자산과 번역
- 테스트/실기 검증 조건
- Sol/Luna 위임 규칙
- 실패 기록 방식

## 5. Stage 방식

큰 작업은 한 번에 전체 적용하지 않습니다.

기본 흐름:

```text
조사
→ 단일 샘플
→ 런타임 검증
→ 전체 적용
→ 자동 검증
→ 변경분만 배포
```

각 Stage 종료 시 다음을 기록합니다.

- 확인된 사실
- 수정 파일
- 해시/크기 등 검증값
- 성공 샘플
- 실패한 접근
- 다음 단계 입력값

## 6. 성공/실패 기록

실패 기록은 폐기물이 아니라 다음 작업의 입력입니다.

기록할 것:

- 어떤 방법을 시도했는지
- 어떤 결과가 나왔는지
- 정적 검증과 실제 런타임 결과가 어떻게 달랐는지
- 재현 조건
- 롤백 기준

다만 게임 전용 실패 기록을 범용 아카이브에 올릴 때는 저작권 자료, 개인 경로, 비공개 데이터 등을 제거하고 재사용 가능한 원리만 남깁니다.

## 7. 실제 프로젝트 파일이 최우선 근거

아카이브는 참고서입니다. 실제 프로젝트의 파일과 실행 결과를 대신하지 않습니다.

따라서 Codex는 항상 다음 순서를 지킵니다.

1. 대상 프로젝트 실제 조사
2. 기존 성공 코드와 승인 산출물 확인
3. 관련 아카이브 노하우 선택
4. 단일 샘플 적용
5. 런타임 검증
6. 성공 근거가 있을 때만 확장
