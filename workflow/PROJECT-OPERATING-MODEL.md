# 게임 한글화 프로젝트 운영 모델

## 1. 한글화 프로젝트 상위 루트

모든 게임 한글화 작품은 기본적으로 다음 상위 루트 아래에 모아 관리합니다.

```text
D:\Codex\한글화 프로젝트
```

게임 하나당 이 상위 루트 바로 아래에 독립된 작품 폴더 하나를 둡니다.

```text
D:\Codex\한글화 프로젝트\<작품 폴더명>
```

명시적인 사용자 지시가 없는 한 새 한글화 프로젝트를 이 상위 루트 밖에 임의로 만들지 않습니다.
다른 작품 폴더는 형제 프로젝트이며, 현재 작업 범위로 지정되지 않은 다른 작품 폴더를 임의로 수정하지 않습니다.

## 2. 신규 프로젝트의 기본 디렉터리 구조

게임이 정해지고 새 프로젝트를 시작하면 다음 여섯 폴더를 공통 기본 베이스로 먼저 만듭니다.

```text
D:\Codex\한글화 프로젝트\<작품 폴더명>\
├─ 01_프로젝트_문서
├─ 02_한글화_작업
├─ 03_검수_프로그램
├─ 04_최종_배포
├─ 05_HD Pack
└─ 버그 리포트
```

- `01_프로젝트_문서`: 분석 보고서, 설계, 결정 기록, 인수인계 성격 문서
- `02_한글화_작업`: 게임 파일 분석, 추출·재삽입, 폰트/UI/대사, 빌더, 중간 분석·staging
- `03_검수_프로그램`: 게임 전용 원장, 안정 row_key, 카테고리화, 검수 프로그램, 최종 CSV 반입
- `04_최종_배포`: 최종 모드·패치·패처·배포 준비 산출물
- `05_HD Pack`: 폴더만 기본 생성하며 사용자 요청 전 실제 제작 금지
- `버그 리포트`: 재현된 오류, 실플레이 문제, 증거와 추적 기록

`D:\Codex\한글화 프로젝트\이상한 환상향 로터스 Lotus Labyrinth`는 폴더 역할을 참고할 수 있는 기존 프로젝트지만, 특정 프로젝트에서 추가된 `.github`, `docs`, `source`, `staging`, `tests`, `tools`, `work`, `셀프 검수 프로그램`, `인수인계`, `작업 자료` 등을 모든 신규 프로젝트의 필수 최상위 폴더로 복제하지 않습니다.

프로젝트별 필요에 따라 추가 폴더를 만들 수는 있습니다. 단, 게임 전용 데이터·코드·번역·로그·오프셋·원본 자산을 다른 게임 프로젝트에서 복사하거나 섞지 않습니다.

기존 프로젝트는 이 구조를 이유로 강제 재배치하지 않습니다. 현재 루트와 성공 자산을 보존하고 필요한 연결 규칙만 보강합니다.

### `05_HD Pack` 운영 경계

`05_HD Pack`은 신규 한글화 프로젝트의 기본 6폴더 중 하나로 **폴더만 미리 생성**합니다.

**사용자가 `HD Pack 제작`, `HD팩 작업`, `텍스처 업스케일` 등으로 명시적으로 요청하기 전에는 실제 텍스처 덤프·업스케일·이미지 재가공·교체 작업을 시작하지 않습니다.**

사용자가 HD Pack 제작 또는 가능성 분석을 명시적으로 요청한 경우 `workflow/HD-PACK-PIPELINE.md`를 읽고, 가능한 플랫폼에서는 ROM/ISO 내부 자산 우선 → 소량 샘플 검증 → 에뮬레이터 dump/hash 매칭 → 신규 dump 증분 처리 원칙을 적용합니다.

HD Pack 결과는 번역/패치 결과와 자동으로 섞어 배포하지 않습니다.

### 한글화 폰트 후보 선정

게임에서 새 한글 폰트를 선택하거나 기존 폰트를 교체해야 하면 `workflow/FONT-SELECTION-POLICY.md`를 먼저 읽습니다.

기본 후보 검색처:

```text
https://font.emulog.app/#fonts
```

작품마다 실제 글리프 셀/타일 크기, BPP, 고정폭/가변폭, 글리프 수, 인코딩, 아틀라스 구조와 표시 픽셀 크기가 다르므로 폰트 이름이나 외형만 보고 바로 적용하지 않습니다.

기본 절차:

```text
게임의 실제 폰트 규격 조사
→ Font Share에서 기술적으로 맞는 후보 약 3개 선정
→ 같은 문구·같은 크기·같은 화면 조건으로 샘플 제작
→ 후보별 장단점과 함께 사용자에게 비교 제시
→ 사용자가 직접 최종 폰트 선택
→ 선택 결과를 프로젝트 확정값으로 기록
```

기술적으로 유효한 후보가 3개 미만이면 억지로 수를 채우지 않습니다.
사용자 선택 전에는 전체 폰트 교체나 대량 반영을 하지 않습니다.
사용자가 확정한 폰트는 이후 AI가 취향 판단만으로 임의 변경하지 않습니다.

### 번역 전 0단계에 들어가기 전 선행 작업

용어집·캐릭터·관계 기준을 만들기 전에 다음 엔지니어링 기반을 먼저 확보합니다.

```text
롬/게임 구조 분석
→ 최소 한글 출력
→ 출력·진행 안전성 게이트
→ 일본어 원문 전체 추출
→ 안정 row_key
→ category/subcategory 분류
→ 게임 전용 검수 프로그램
→ 번역 전 0단계 기준자료
```

기술 안전성 게이트는 `workflow/EARLY-TEXT-RUNTIME-GATE.md`를 따릅니다. 한글이 표시되는지만 확인하지 않고 `[n]` 유지/삭제/이동/추가/개수 변경, 반각/전각, 가로폭, 최대 줄 수, RSC/인코딩, 다음 대사·선택지·다음 장면 진행을 확인합니다. 안전한 경로가 없으면 대량 번역으로 넘어가지 않습니다.

기술 게이트 통과 후 일본어 원문 전체를 추출해 번역문과 독립적인 안정 `row_key`를 만들고, `category/subcategory`로 문자열의 기능을 분류합니다. 단순 일본어 문장 덤프는 검수 원장으로 사용하지 않습니다.

용어집을 최종화하기 전에 `03_검수_프로그램`에 게임 전용 검수 프로그램을 준비합니다.

- 프로그램 구조·원장·최종 CSV 반입의 기본 베이스: `D:\Codex\# 검수 프로그램\EVE 고스트 에너미즈`
- 카테고리/세부분류 방식 참고: `D:\Codex\# 검수 프로그램\이상한 환상향 로터스 라비린스`

재사용 가능한 구조와 기능만 참고하고 EVE/로터스의 실제 게임 데이터·용어·관계·오프셋·확정 번역은 새 프로젝트에 섞지 않습니다.

그 뒤 `review/PRE-TRANSLATION-SETUP.md`를 적용해 캐릭터명·세계관/아이템/스킬/시스템 용어, 성격·말투, 화자 → 청자 방향별 관계, 방향별 반말/존댓말·호칭·예외와 근거 상태를 구축합니다. `A → B`와 `B → A`는 독립 규칙이며 대칭 관계를 기본 가정하지 않습니다.

### Google Drive는 휴대폰/웹 검수용 실제 작업장

PC 동기화 루트는 다음입니다.

```text
F:\내 드라이브\검수 프로그램\<게임명>\
├─ 01_최신_용어집
├─ 02_검수_필수파일
└─ 03_검수_수정_CSV
```

- `01_최신_용어집`: 최신 용어 기준과 confirmed/provisional/HOLD 상태
- `02_검수_필수파일`: 캐릭터·말투·방향별 관계·출력 규격·출처·1차/2차/3차 전용 지시문
- `03_검수_수정_CSV`: 게임 전용 검수 프로그램 최신 원장에서 내보낸 `row_key/category/subcategory`가 살아 있는 검수 CSV

이 구조는 PC를 켜두지 않고 휴대폰/웹 ChatGPT만으로 검수를 계속하기 위한 것입니다. Drive 동기화와 등록 파일 재조회가 끝나기 전에는 0단계 완료나 1차 시작 가능이라고 보고하지 않습니다.

검수는 전체 대사집을 1차 1,000행 → 2차 1,000행 → 3차 500행으로 각각 다시 훑습니다. 마지막에는 `<게임약칭>_최종대사_수정_누적.csv`를 게임 전용 검수 프로그램 최신 원장에 반입하고 모드/패치와 실제 플레이 검증으로 이어갑니다.

## 3. 프로젝트 기본 단위

한 게임은 하나의 독립된 한글화 도메인으로 관리합니다.

```text
게임 1개
  → D:\Codex\한글화 프로젝트 아래 작품 폴더 1개
  → Codex 한글화 프로젝트 1개
  → 게임 전용 검수 프로그램 1개
  → 게임 전용 Google Drive 검수 작업공간 1개
```

다른 게임에서 성공한 코드나 분석법은 참고할 수 있지만, 게임별 데이터와 판정 규칙은 자동으로 섞지 않습니다.

## 4. Codex와 작업자 계층의 역할 분리

한글화 엔지니어링은 한 모델이 전부 직접 수행하는 구조가 아니라 **감독관 → 전문 실무 책임자 → 단순 작업자 → 외부 전문가** 구조로 운영합니다.

### GPT-5.6 Sol High: 소장 / 감독관

Sol High는 프로젝트 전체를 파악하고 다음을 담당합니다.

- 사용자 요구와 성공 조건 해석
- 작업 분해
- 위험도·난이도 판단
- 작업자 배차
- 결과 비교와 충돌 해결
- 실제 diff·테스트·런타임 근거 검증
- 최종 통합

Sol이 직접 할 수 있다는 이유만으로 일반 실무를 혼자 수행하지 않습니다.

### DevSpace + Web GPT-5.6 Sol XHIGH: 분야별 과장 / 기본 전문 실무 책임자

일반~상당 난도의 실제 한글화 엔지니어링 실무를 기본적으로 담당합니다.

- 게임 파일/자산 분석
- 텍스트/자산 추출·재삽입 경로 조사
- 폰트/UI/영상/바이너리의 일반 구현 작업
- 빌더·패처·검수 도구 구현과 검토
- 중간~상당 난도 디버깅
- 여러 파일을 묶은 기술 조사와 설계 검토

전문 실무에 Web Sol XHIGH를 사용할 때는 DevSpace `open_workspace`를 실제 호출해 프로젝트 연결 상태를 확인합니다.

### GPT-5.6 Luna XHIGH: 기사 / 저위험 단순 작업자

- 파일·문자열 위치 조사
- 목록화와 반복 검색
- CSV/JSON/Markdown 정리
- 확정 규칙에 따른 일괄 처리
- 테스트 반복
- 해시·크기·개수 비교
- 로그 집계

새 설계 판단, 애매한 바이너리 추론, 어려운 원인 분석, 근거가 갈리는 번역·관계·존대 판정은 맡기지 않습니다.

### GPT-6 Astra Medium: 외주 전문업체

내부 실무진에게 맡기기 어려운 고난도 구현·디버깅을 담당합니다. 처음부터 명백히 Astra급 문제라면 하위 작업자를 일부러 실패시키지 않습니다.

### DevSpace + Web GPT-6 Pro: 최고급 외부 전문가

Astra급 접근으로도 풀리지 않거나 최고 수준 추론이 필요한 난제를 담당합니다.

### 웹 ChatGPT + Google Drive 언어 검수

Google Drive의 게임별 CSV와 기준 자료를 사용해 대량 번역/검수를 수행합니다.

- 0단계: 용어집·캐릭터·관계·말투 기준자료 조사와 보강
- 1차: 전체 대사집을 1,000행 단위로 기초 검수
- 2차: 1차 결과 전체를 다시 1,000행 단위로 자연화와 캐릭터 말투 보정
- 3차: 2차 결과 전체를 다시 500행 단위로 가장 엄격한 최종 정밀검수

Codex가 대량 대사 번역을 대신 수행하는 것을 기본 흐름으로 삼지 않습니다.

## 5. 공통 코드 재사용과 게임 데이터 격리

재사용 가능:

- 범용 CSV 파서
- 해시 검증기
- diff/manifest 생성기
- 공통 UI 컴포넌트
- 테스트 헬퍼
- 형식이 실제로 같다고 검증된 추출/빌드 코드

자동 재사용 금지:

- 용어집
- 캐릭터 정보
- 관계도
- 반말/존댓말
- 말투 규칙
- 런타임 오프셋
- 파일 포맷 가정
- 승인 번역
- 승인된 작품별 폰트 선택값
- 플레이 검수 결론
- 다른 게임의 HD Pack 원본/업스케일 결과/교체 매핑

같은 시리즈, 같은 엔진, 비슷한 파일명이라는 이유만으로 호환성을 확정하지 않습니다.

## 6. 프로젝트 `AGENTS.md` 우선

대상 프로젝트에 `AGENTS.md`가 있으면 아카이브의 일반 지침보다 해당 프로젝트 규칙을 우선합니다.

`AGENTS.md`에는 최소한 다음을 둡니다.

- 정확한 게임/프로젝트 범위
- 수정 허용 루트
- 건드리면 안 되는 다른 프로젝트
- 지원 버전과 기준 원본
- 이미 승인된 자산과 번역
- 번역 전 기준자료 준비 상태
- 승인된 폰트와 폰트 규격
- 테스트/실기 검증 조건
- 모델 위임 규칙
- 실패 기록 방식
- PS3 이하 작품이라면 `05_HD Pack`의 사용 여부와 현재 승인 상태

## 7. Stage 방식

큰 작업은 한 번에 전체 적용하지 않습니다.

기본 흐름:

```text
조사
→ 단일 샘플
→ 런타임 검증
→ 전체 적용
→ 자동 검증
→ 변경분만 배포
```

각 Stage 종료 시 다음을 기록합니다.

- 확인된 사실
- 수정 파일
- 해시/크기 등 검증값
- 성공 샘플
- 실패한 접근
- 다음 단계 입력값

## 8. 성공/실패 기록

실패 기록은 폐기물이 아니라 다음 작업의 입력입니다.

기록할 것:

- 어떤 방법을 시도했는지
- 어떤 결과가 나왔는지
- 정적 검증과 실제 런타임 결과가 어떻게 달랐는지
- 재현 조건
- 롤백 기준

다만 게임 전용 실패 기록을 범용 아카이브에 올릴 때는 저작권 자료, 개인 경로, 비공개 데이터 등을 제거하고 재사용 가능한 원리만 남깁니다.

## 9. 실제 프로젝트 파일이 최우선 근거

아카이브는 참고서입니다. 실제 프로젝트의 파일과 실행 결과를 대신하지 않습니다.

따라서 Codex는 항상 다음 순서를 지킵니다.

1. 대상 프로젝트 실제 조사
2. 기존 성공 코드와 승인 산출물 확인
3. 관련 아카이브 노하우 선택
4. 단일 샘플 적용
5. 런타임 검증
6. 성공 근거가 있을 때만 확장
