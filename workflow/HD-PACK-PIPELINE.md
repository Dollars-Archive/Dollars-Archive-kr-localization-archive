# HD Pack 제작 표준 파이프라인

이 문서는 사용자가 **HD Pack 제작 또는 HD Pack 가능성 분석을 명시적으로 요청했을 때만** 적용합니다.

`05_HD Pack/` 폴더가 존재하거나 한글화 작업을 진행 중이라는 이유만으로 이 작업을 자동 시작하지 않습니다.

## 0. 기본 철학

HD Pack 제작의 기본 출발점은 장시간 플레이 덤프가 아닙니다.

가능하면 먼저 게임의 ROM/ISO/디스크 이미지 내부에서 2D 자산을 직접 추출하고, 추출 가능한 자산으로 **기본 베이스 HD Pack**을 만든 뒤 실제 플레이 중 새로 발견되는 런타임 텍스처만 증분 처리합니다.

```text
ROM / ISO / 디스크 이미지
→ 내부 자산 구조 분석
→ 추출 가능한 2D 자산 추출
→ 소량 샘플 검증
→ 분류
→ 업스케일 가능한 베이스 자산 확보
→ 에뮬레이터 texture dump와 대응 관계 분석
→ 베이스 HD Pack 구축
→ 실제 플레이
→ 기존 베이스에 없는 신규 dump만 추가 처리
→ 점진적 HD Pack 완성
```

따라서 목표는 다음과 같습니다.

- 게임을 처음부터 끝까지 플레이하면서 모든 텍스처를 하나씩 덤프하는 작업량을 가능한 한 줄입니다.
- ROM/ISO 내부에서 이미 존재하는 원본 2D 자산을 최대한 재사용합니다.
- 런타임에서만 생성되거나 부분 합성되는 자산은 실제 플레이 dump로 보충합니다.
- ROM 내부 자산과 에뮬레이터 texture dump 사이의 자동 또는 반자동 매칭 도구 제작 가능성을 우선 검토합니다.

플랫폼별 에뮬레이터와 texture replacement 규칙은 다르므로, 공통 원칙은 유지하되 실제 해시·파일명·덤프 구조·교체 규칙은 대상 플랫폼에서 직접 확인합니다.

---

# 1. 단계 구분

HD Pack 작업은 최소 두 단계로 나눕니다.

## Stage A — 구조 분석 및 자동화 가능성 조사

처음에는 다음만 수행합니다.

- ROM/ISO 구조 조사
- 이미지/컨테이너 포맷 조사
- 소량 샘플 추출
- 런타임 dump와의 대응 방식 조사
- 자동 매칭 가능성 평가
- 플레이 요구량 평가
- 향후 도구 설계

이 단계에서는 대량 업스케일이나 전체 팩 제작을 하지 않습니다.

## Stage B — 실제 HD Pack 제작

Stage A 결과를 사용자가 확인하고 실제 제작을 명시적으로 승인한 뒤 진행합니다.

Stage B에서도 가능한 경우 먼저 ROM/ISO 기반 베이스팩을 만들고, 이후 플레이 중 신규 dump만 증분 추가합니다.

---

# 2. 작업 시작 전 안전 규칙

대상 작품 폴더, ROM/ISO 또는 디스크 이미지의 위치와 버전을 먼저 확인합니다.

원본은 항상 보존합니다.

- 원본 ISO/ROM 수정 금지
- 원본 파일 덮어쓰기 금지
- 원본 삭제 금지
- 분석 결과를 원본 파일이 있는 위치에 섞어 쓰지 않음
- 분석용 추출물은 해당 작품의 `05_HD Pack/`, `work/` 또는 별도 `analysis/` 아래에 둠
- 플랫폼, 지역판, 게임 ID, 리비전이 다르면 같은 자산 구조라고 가정하지 않음

가능하면 분석 시작 시 원본 파일의 해시와 크기를 기록합니다.

---

# 3. ROM / ISO 파일 구조 조사

전체 파일 트리와 큰 파일/반복 파일군을 먼저 조사합니다.

확장자만으로 판단하지 않고 다음을 함께 확인합니다.

- magic / header
- 파일 크기 분포
- 반복 헤더
- 오프셋 테이블
- 압축 흔적
- 팔레트/CLUT 흔적
- 이미지 크기로 추정 가능한 메타데이터
- 내부 파일명 또는 경로 문자열
- 동일 포맷 파일군의 개수와 용량 패턴

PS2 예시 조사 후보:

- TM2 / TIM2
- TIM
- TEX
- ARC
- PAC
- PAK
- DAT
- BIN
- IMG
- GIM
- PSS
- M2V
- IPU
- 게임 고유 확장자 또는 확장자 없는 컨테이너

다른 플랫폼에서도 같은 원칙으로 해당 기종의 대표 포맷과 게임 고유 컨테이너를 조사합니다.

# 4. 2D 이미지 자산 분류

가능한 경우 다음 범주로 분류합니다.

```text
extracted/
├─ characters/
├─ backgrounds/
├─ events/
├─ ui/
├─ effects/
├─ fonts/
├─ unknown/
└─ video_related/
```

## 캐릭터

다음을 확인합니다.

- 전신/반신 스탠딩
- 얼굴
- 눈
- 입
- 표정 차분
- 의상 차분
- 캐릭터별 atlas / sprite sheet
- 파츠별 합성 여부

완성 이미지가 하나의 파일로 저장되는지, BODY/FACE/EYE/MOUTH/HAIR 등 여러 레이어로 분리되어 런타임에 합성되는지 확인합니다.

## 배경

- 독립 이미지인지
- atlas인지
- 타일 분할인지
- 압축 컨테이너 안에 있는지
- 런타임에서 여러 조각을 합성하는지

## 이벤트 CG

- 정지 이미지
- 여러 레이어로 구성된 연출
- 애니메이션
- 실제 동영상

으로 구분합니다.

## UI

- 메뉴
- 대화창
- 아이콘
- 버튼
- 선택지
- 프레임
- 숫자/게이지
- 폰트 이미지

등을 별도 분류합니다.

# 5. FMV / 컷신 분리

컷신을 반드시 다음처럼 구분합니다.

## A. 이미지 기반 연출

정지 CG, 이미지 레이어, 스프라이트 애니메이션 등으로 구성된 경우 texture replacement 대상이 될 수 있습니다.

## B. 실제 동영상

PSS / MPEG2 / IPU / M2V 등 실제 비디오 스트림이라면 texture replacement와 분리합니다.

영상은 일반적으로 다음 별도 파이프라인이 더 적합할 수 있습니다.

```text
영상 추출
→ 업스케일
→ 재인코딩
→ 게임 데이터 교체
```

그러나 Stage A에서는 영상 재인코딩이나 게임 데이터 교체를 하지 않습니다.

# 6. 이미지 추출 가능성 평가

발견한 포맷마다 다음 등급으로 평가합니다.

- 기존 오픈소스 도구로 즉시 추출 가능
- Noesis 등 범용 도구로 처리 가능
- QuickBMS 스크립트가 존재하거나 작성 가능
- 간단한 Python 추출기 제작 가능
- 압축 해제부터 분석 필요
- 포맷 리버스 엔지니어링 필요

가능하면 대표 샘플 몇 개만 실제 추출해 정상 이미지인지 확인합니다.

대량 추출/변환은 Stage A에서 하지 않습니다.

샘플 검증 시 최소한 다음을 기록합니다.

- 원본 파일 경로
- 포맷
- 폭/높이
- 색상 형식
- 팔레트/알파 여부
- 추출 방법
- 결과 이미지 해시
- 시각적으로 정상인지

---

# 7. 에뮬레이터 Texture Replacement 대응 분석

최종 목표는 ROM/ISO 내부 자산과 런타임 texture dump를 연결하는 것입니다.

PS2 / PCSX2 예:

```text
ISO 내부 원본
CHAR_A_NORMAL.tm2
↓ 추출
characters/CHAR_A_NORMAL.png
↓ 업스케일
upscaled/characters/CHAR_A_NORMAL.png
↓ PCSX2 dump와 대응 확인
replacements/<PCSX2_TEXTURE_ID>.png
```

대상 게임에서 다음을 직접 조사합니다.

- 원본 이미지와 dump가 픽셀 단위로 동일한지
- 해상도만 다른지
- crop되어 업로드되는지
- atlas 전체가 업로드되는지
- atlas 일부만 텍스처로 사용되는지
- 타일 단위로 잘리는지
- CLUT/palette 변환이 있는지
- 알파 채널이 변하는지
- 색상 공간 또는 포맷 변환이 있는지
- 런타임에서 파츠 합성 후 업로드되는지
- 확대/축소 또는 패딩이 생기는지
- 동일 원본이 여러 런타임 텍스처로 갈라지는지
- 여러 원본이 하나의 런타임 텍스처로 합쳐지는지

에뮬레이터의 해시/파일명 규칙을 ROM 원본 파일명과 동일하다고 가정하지 않습니다.

---

# 8. 자동 이미지 매칭 가능성

ROM/ISO 추출 이미지와 런타임 dump 사이를 사람이 일일이 비교하지 않도록 자동 매칭 가능성을 우선 분석합니다.

후보 방법:

- exact pixel hash
- 크기 정규화 후 exact 비교
- perceptual hash
- SSIM
- template matching
- crop/subimage 탐색
- alpha 제거 또는 alpha 정규화 후 비교
- palette / CLUT 정규화
- 색상 채널 변환 후 비교
- atlas 부분 이미지 탐색
- 타일 조합 탐색
- 특징점 또는 경량 이미지 임베딩 비교

목표 출력 예:

```json
{
  "pcsx2_hash_001": {
    "source": "characters/char001.png",
    "confidence": 0.998,
    "method": "crop+ssim",
    "notes": "alpha normalized"
  }
}
```

매칭기는 가능한 경우 상위 후보 여러 개와 confidence를 함께 남깁니다.

```text
PCSX2 dump A
→ ISO image X 99.8%
→ ISO image Y 72.1%
→ ISO image Z 41.3%
```

낮은 confidence는 자동 확정하지 않고 사람 검토 대상으로 둡니다.

# 9. 플레이 요구량 분석

가장 중요한 판정 중 하나입니다.

게임을 처음부터 끝까지 플레이해야 하는지부터 의심합니다.

다음 우회 수단을 조사합니다.

- ROM/ISO 직접 추출
- CG 갤러리
- 캐릭터 갤러리
- 회상 모드
- 사운드/앨범/이벤트 갤러리
- 100% 세이브
- 디버그 기능
- 이벤트 점프
- 챕터 선택
- 스크립트 분석
- 메뉴에서 반복 표시 가능한 UI
- 안전한 범위의 게임 내 해금 기능

Stage A에서는 세이브 적용, 치트 적용, 장시간 플레이, 게임 실행 파일 패치를 자동으로 수행하지 않습니다. 필요하면 가능성만 조사하고 사용자 승인 범위를 따릅니다.

최종적으로 다음과 같이 판정합니다.

### A

거의 모든 핵심 2D 자산을 ROM/ISO에서 직접 추출 가능.
플레이는 런타임 hash / texture ID 수집과 누락 확인용으로 최소화 가능.

### B

원본 자산 추출은 가능하지만 런타임 texture 대응 때문에 상당한 플레이 또는 갤러리 순회가 필요.

### C

런타임 합성/동적 생성이 많아 ROM 기반 자동화 효율이 낮고 실제 플레이 dump가 주력이 되어야 함.

### D

위 분류에 맞지 않는 특수 구조. 이유를 구체적으로 기록.

사용자가 별도로 정의한 플레이 요구량 기준이 있으면 그 기준을 우선합니다.

# 10. 베이스팩 우선 + 증분 덤프 방식

구조 분석 결과가 허용한다면 실제 제작은 다음 순서를 기본으로 합니다.

## 1단계 — Base Asset Pack

ROM/ISO에서 직접 추출 가능한 스탠딩, 배경, 이벤트 CG, UI 등 기본 자산을 먼저 HD화합니다.

이 단계에서 가능한 한 많은 원본 자산을 준비해 둡니다.

## 2단계 — Runtime Mapping

짧은 플레이, 갤러리, 메뉴, 회상 모드 등으로 texture dump/hash를 수집하고 베이스 자산과 자동/반자동 매칭합니다.

## 3단계 — Delta Collection

이후 실제 플레이에서 새 dump가 나타나면:

```text
신규 dump 발견
→ 기존 mapping.json 검색
→ 기존 소스와 매칭되는지 확인
→ 이미 HD화된 소스면 replacement만 연결
→ 완전히 새로운 런타임 자산이면 신규 처리
→ mapping.json 갱신
```

즉, **플레이할 때마다 모든 텍스처를 다시 작업하지 않고, 기존 베이스에 없는 신규 자산만 추가**합니다.

이 증분 방식이 이 문서의 기본 제작 전략입니다.

# 11. 향후 자동화 도구 구조

구조 분석이 성공하면 다음 형태의 전용 또는 범용 도구를 검토합니다.

입력:

```text
GAME.ISO / ROM
emulator_dumps/
```

중간/출력:

```text
extracted/
├─ characters/
├─ backgrounds/
├─ events/
├─ ui/
└─ unknown/

upscaled/

mapping.json

replacements/
```

예:

```json
{
  "pcsx2_hash_001": {
    "source": "characters/char001.png",
    "confidence": 0.998
  }
}
```

장기 목표:

```text
ROM / ISO
→ 자산 추출
→ 분류
→ 업스케일
→ 에뮬레이터 dump 자동 매칭
→ replacements 생성
→ 플레이 중 신규 dump 감지
→ 신규 자산만 증분 처리
```

범용 도구로 만들 때는 플랫폼별 adapter를 분리합니다.

예:

```text
core/
  image_matcher
  asset_catalog
  mapping_store
  incremental_detector

adapters/
  pcsx2/
  <other emulator>/

extractors/
  ps2/
  <platform or game specific>/
```

게임 고유 포맷은 공통 코어와 분리합니다.

# 12. Stage A에서 하지 말 것

사용자의 별도 승인이 없는 한 이번 분석 단계에서는 다음을 하지 않습니다.

- 원본 ROM/ISO 수정
- 실행 파일 패치
- 대량 AI 업스케일
- 수천 장 이미지 대량 변환
- FMV 재인코딩
- 전체 HD Texture Pack 제작
- 장시간 자동 플레이
- 대량 texture dump 수집
- 세이브 다운로드/적용
- 치트 적용
- 사용자가 요청하지 않은 배포

구조 분석과 작은 샘플 검증까지만 수행합니다.

마지막에는 반드시 한 줄 결론을 작성합니다.

예:

> 이 게임은 ISO에서 스탠딩/배경/CG 대부분을 직접 추출할 수 있으므로 실제 플레이는 texture ID 수집과 누락 보완용으로 최소화할 수 있으며, ROM-first HD Pack 반자동화에 적합하다.

또는 실제 조사 결과에 맞는 결론을 작성합니다.

추측만으로 판정하지 않고 실제 파일 구조, 헤더, 소량 샘플 추출, 런타임 dump 비교 등 확인된 근거를 구분해서 제시합니다.

# 14. 결과의 우선순위

HD Pack 작업에서도 다음 우선순위를 지킵니다.

1. 실제 파일 구조와 샘플 검증 결과
2. 실제 에뮬레이터 dump / replacement 동작
3. 게임별 확정 매핑과 사용자가 직접 확인한 결과
4. 포맷 문서와 기존 도구
5. AI 추론

AI 추론만으로 대량 변환 또는 전체 팩 제작을 시작하지 않습니다.
