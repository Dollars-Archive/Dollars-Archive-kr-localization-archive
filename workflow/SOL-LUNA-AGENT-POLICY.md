# 한글화 모델 라우팅 정책

> 파일명은 기존 호환을 위해 `SOL-LUNA-AGENT-POLICY.md`를 유지하지만, 현재 정책은 Sol / Astra / Luna / Web GPT 전체를 다룹니다.

## 1. 기본 모델 구성

한글화 프로젝트의 기본 라우팅은 다음과 같습니다.

```text
총괄·기본 작업        → GPT-5.6 Sol / High
고난도 구현·디버깅    → GPT-6 Astra / Medium
단순·반복·명확한 작업 → GPT-5.6 Luna / XHIGH
고추론 난제            → DevSpace Tunnel 경유 Web GPT 6 Pro
중간 난이도            → Web GPT XHIGH
Terra                   → 기본 워크플로에서 사용하지 않음
```

이 표는 모델의 절대적인 성능 순위가 아니라 **이 한글화 아카이브에서 사용하는 역할 분담 기준**입니다.

## 2. 가장 중요한 원칙: Sol이 총괄한다

Sol High는 기본 작업자이자 프로젝트의 계획자·통합자·최종 검토자입니다.

담당:

- 요구사항 해석
- 현재 프로젝트 상태 파악
- 전체 계획
- 구조/아키텍처 판단
- 위험도와 난이도 판정
- 서브에이전트 또는 Web GPT 위임 여부 결정
- 충돌 해결
- 결과 통합
- 최종 diff/테스트/산출물 검토

**작업마다 여러 모델을 억지로 호출하지 않습니다.**
Sol High가 충분히 잘 처리할 수 있고 위임 비용이 더 크면 Sol이 그대로 끝냅니다.

보통은 다음 구조를 목표로 합니다.

```text
Sol High 단독
또는
Sol High + 필요한 전문 작업자 1명
```

매 작업마다 모든 모델을 순차 호출하는 구조는 금지합니다.

## 3. 난이도별 자동 배차

### Sol High

기본값입니다.

- 일반적인 게임 파일 분석
- 계획 수립
- 구현과 수정
- 결과 취합
- 다른 작업자의 결과 검토
- 프로젝트 문맥을 이미 많이 쌓은 상태에서 이어지는 관련 작업

작은 작업이라는 이유만으로 이미 문맥을 가진 Sol에서 다른 모델로 불필요하게 넘기지 않습니다.

### Astra Medium

처음부터 고난도라고 판단되는 작업에 사용합니다.

예:

- 복잡한 바이너리·실행 파일 구조 분석
- 여러 계층이 얽힌 저장/로드·런타임 버그
- 기존 설계의 구조적 한계 진단
- 어려운 패처/빌더 구현
- 일반적인 접근으로 원인이 설명되지 않는 디버깅
- 여러 원인 후보를 동시에 비교해야 하는 기술 판단

Luna나 Sol을 일부러 먼저 실패시킨 뒤 Astra를 부르는 식으로 운영하지 않습니다.
처음부터 고난도이면 바로 Astra를 고려합니다.

### Luna XHIGH

범위와 완료 조건이 명확한 작업에 사용합니다.

예:

- 반복적인 구현
- 규칙이 확정된 일괄 수정
- CSV/JSON/Markdown 생성·정리
- 정적 검증
- 파일/문자열 위치 조사
- 기존 코드 패턴 확인
- 테스트 작성·실행
- 결과 비교
- 확정된 방식에 따른 기계적 처리

Luna는 다음을 임의로 결정하지 않습니다.

- 새로운 아키텍처 결정
- 프로젝트 범위 확장
- 승인된 규칙 재정의
- 실제 플레이로 확정한 번역 수정
- 다른 게임 프로젝트 데이터 혼용
- 근거 없는 대량 수정

### Web GPT XHIGH

**Luna XHIGH에게는 다소 어렵지만 Sol High를 계속 사용할 정도는 아닌 중간 난이도 작업**에 사용합니다.

예:

- 독립적으로 분리 가능한 중간 수준 분석
- 비교 검토
- 보조 설계 검토
- Sol이 직접 붙잡고 있을 필요가 없는 추론 작업

자동 호출 가능한 경로가 실제로 제공될 때만 자동으로 사용합니다.
실행하지 않은 Web GPT 작업을 실행했다고 보고하지 않습니다.

### Web GPT 6 Pro

**고추론이 필요한 난제**를 별도 시각으로 분석할 때 사용합니다.

예:

- 여러 번의 합리적인 시도에도 원인이 불명확한 문제
- 기존 가정을 처음부터 재검토해야 하는 문제
- 복잡한 바이너리·런타임·세이브 구조의 원인 분석
- 구현 전에 매우 깊은 기술 판단이 필요한 문제
- Sol/Astra 작업 전에 강력한 독립 분석이 도움이 되는 문제

Web GPT 6 Pro의 분석 결과 역시 최종 진실이 아닙니다.
Sol이 프로젝트 실제 파일, 테스트, 런타임 근거와 비교한 뒤 채택합니다.

## 4. Web GPT / DevSpace Tunnel 운용 규칙

Web GPT에 프로젝트 작업을 의뢰해야 할 때는 연결 상태를 추측하지 않습니다.

1. 대상 프로젝트의 정확한 루트를 확인합니다.
2. **DevSpace Tunnel의 `open_workspace`를 실제 호출합니다.**
3. 호출 성공 시 해당 workspace를 기준으로 즉시 작업을 이어갑니다.
4. 환경이 Web GPT 자동 의뢰 동작까지 실제로 제공하면 자동 전달을 우선합니다.
5. 자동 전달 기능이 없거나 사용자 동작이 필수이면 Sol이 다음을 먼저 준비합니다.
   - 완성된 의뢰 프롬프트
   - 작업 목표
   - 필요한 파일/경로
   - 현재까지 확인한 사실
   - 이미 실패한 접근
   - 금지 사항
   - 원하는 결과 형식
6. 사용자는 준비된 내용을 Web GPT에 전달하기만 하면 되도록 합니다. 사용자에게 문제를 처음부터 다시 설명하게 하지 않습니다.

### DevSpace 오류 판정

- `tool disabled` 또는 `FORBIDDEN`
  - MCP 네트워크 장애로 단정하지 않습니다.
  - 현재 ChatGPT 세션/앱에서 developer MCP 사용이 활성화되지 않은 상태로 판정합니다.
  - DevSpace 수동 실행, 재설치, Tailscale, Watchdog, OAuth 변경을 지시하지 않습니다.
- `502` 또는 `network_error`
  - 실제 MCP 연결 경로 문제 가능성이 있는 경우입니다.
  - 일시 장애 가능성을 고려해 **최소 1분 간격으로 최대 5회 재시도**합니다.
  - 그래도 실패할 때만 연결 경로를 조사하거나 사용자에게 상태 확인을 요청합니다.
- 실제 호출을 하지 않은 상태에서 "DevSpace 연결됨/끊김"을 추측해 보고하지 않습니다.

## 5. 위임 손익 규칙

위임은 다음 중 하나 이상의 실질적인 이득이 있을 때만 합니다.

- 해당 모델이 작업 유형에 더 적합함
- 독립 작업으로 분리해 전체 시간을 줄일 수 있음
- Sol의 비싼 추론을 아낄 수 있음
- 별도 시각의 검토가 오류 위험을 낮춤

다음 상황에서는 위임하지 않습니다.

- Sol이 이미 충분한 문맥을 가지고 있고 금방 끝낼 수 있음
- 설명·인계·재검토 비용이 실제 작업보다 큼
- 같은 파일을 동시에 수정하게 됨
- 작업 범위가 아직 불명확함
- 단지 여러 모델을 사용했다는 모양을 만들기 위한 위임

## 6. 병렬 작업 규칙

병렬 위임은 서로 독립적인 작업에만 사용합니다.

좋은 예:

```text
Luna A → 옵션 텍스처 구조 조사
Luna B → 기존 빌더 조사
Luna C → 테스트 로그 정리
```

피해야 할 예:

```text
두 작업자가 동시에 같은 빌더 파일 수정
두 작업자가 같은 staging 폴더에 동시에 쓰기
한 작업 결과가 다른 작업 입력인데 병렬 실행
```

공유 상태가 있으면 순차 실행합니다.

## 7. 서브에이전트 결과 반환 규칙

작업자는 가능하면 다음을 반환합니다.

- 확인된 사실
- 재현 가능한 근거
- 수정/조사한 파일
- 변경 내용
- 실행한 테스트와 실제 결과
- 실패한 접근
- 미해결 사항
- 선택지가 있다면 각 선택지의 영향

"완료했습니다"라는 문장만으로는 완료로 인정하지 않습니다.

## 8. Sol 최종 검토

다른 모델의 결과를 받았다고 바로 원본에 반영하거나 완료 처리하지 않습니다.

Sol은 최소한 다음을 확인합니다.

1. 작업 범위 준수
2. 다른 프로젝트 침범 여부
3. 사용자가 실제 플레이에서 확정한 값 보존
4. diff 또는 실제 변경 파일
5. 테스트 결과
6. 기존 성공 자산 보존
7. 필요 시 런타임 검증
8. 최종 산출물 재조회

모델의 응답 성공과 실제 패치 성공을 구분합니다.

```text
AI 응답 완료 ≠ 구현 완료 ≠ 정적 검증 완료 ≠ 실제 게임 검증 완료
```

## 9. 실제 플레이 확정값 보호

우선순위는 다음과 같습니다.

1. 사용자가 실제 플레이 중 직접 확인하고 확정한 수정
2. 게임 내 실제 문맥과 대사 근거
3. 등록된 원장/용어집/관계/말투 규칙
4. AI 분석 또는 자동 분석 결과

어떤 모델도 AI 판단만으로 1번 값을 덮어쓰지 않습니다.

## 10. 프로젝트별 설정

공통 라우팅 정책은 모든 게임에서 재사용할 수 있지만 실제 게임 데이터는 섞지 않습니다.

각 게임은 별도 프로젝트에서 다음을 독립 관리합니다.

- `AGENTS.md`
- 용어집
- 관계도
- 말투 규칙
- 원장
- 패치 규칙
- 원본 해시
- 오프셋
- 검수 프로그램
- 실제 플레이 확정값

게임별 `AGENTS.md`가 이 공통 정책보다 더 구체적인 안전 규칙을 가지고 있다면 게임별 규칙을 우선합니다.

## 11. 모델 또는 기능이 실제로 없을 때

문서에 적힌 모델이나 호출 경로가 현재 실행 환경에서 실제로 제공되는지 확인합니다.

- 사용자가 고정한 모델/추론 강도를 임의의 다른 모델로 조용히 대체하지 않습니다.
- 사용할 수 없으면 해당 작업만 Sol이 계속 처리하거나, 필요한 경우 사용자에게 준비된 수동 의뢰 절차를 제공합니다.
- 새 유료 API, 새 공급자, 새로운 외부 데이터 전송을 자동으로 시작하지 않습니다.
- 실행하지 않은 모델 호출을 실행했다고 표시하지 않습니다.
