# Sol / Luna 에이전트 운영 정책

## 기본 모델 구성

```text
메인 에이전트: GPT-5.6 Sol / Medium
서브에이전트: GPT-5.6 Luna / XHIGH
Terra: 기본 워크플로에서 사용하지 않음
```

## 1. Sol 역할

Sol은 프로젝트의 계획자·통합자·최종 검토자입니다.

담당:

- 요구사항 해석
- 전체 계획
- 구조/아키텍처 판단
- 위험한 변경의 방향 결정
- 작업 분해
- Luna 위임
- 충돌 해결
- 결과 통합
- 최종 diff/테스트/산출물 검토

새로운 기술 판단이나 프로젝트 범위 변경은 Sol이 책임집니다.

## 2. Luna 역할

Luna는 범위가 명확한 실행 작업을 담당합니다.

권장 작업:

- 읽기 전용 조사
- 파일/문자열 위치 조사
- 로그 분석
- 기존 코드 패턴 확인
- 반복적인 구현
- 테스트 작성/실행
- CSV/JSON/Markdown 생성
- 정적 검증
- 결과 비교
- 확정된 방식에 따른 일괄 처리

Luna는 다음을 임의로 하지 않습니다.

- 새로운 아키텍처 결정
- 프로젝트 범위 확장
- 승인된 규칙 재정의
- 다른 게임 프로젝트의 데이터를 가져와 적용
- 근거 없는 대량 수정

## 3. 권장 서브에이전트 역할

### `luna_reader`

읽기/조사 전용.

- 파일 구조
- 기존 빌더
- 문자열 위치
- 로그
- 테스트 실패 원인 후보
- 성공 샘플과 실패 기록

가능하면 쓰기 권한 없이 운영합니다.

### `luna_worker`

구현/테스트 전용.

- Sol이 확정한 방식 구현
- 지정 파일 수정
- 테스트 작성
- 테스트 실행
- 산출물 생성
- 결과 요약

## 4. 병렬 작업 규칙

병렬 위임은 독립적인 작업에만 사용합니다.

좋은 예:

```text
Luna A → 옵션 텍스처 구조 조사
Luna B → 기존 빌더 조사
Luna C → 테스트 로그 분석
```

피해야 할 예:

```text
Luna A/B가 동시에 같은 빌더 파일 수정
Luna A/B가 같은 staging 폴더에 동시에 쓰기
서로 결과에 의존하는 작업을 동시에 실행
```

공유 상태가 있거나 한 작업의 결과가 다른 작업의 입력이면 순차 실행합니다.

## 5. Luna → Sol 에스컬레이션

다음 상황에서는 Luna가 임의로 결정하지 않고 Sol에게 반환합니다.

- 기존 계획과 실제 파일이 다름
- 아키텍처 변경이 필요함
- 지정 범위를 넘어선 수정이 필요함
- 기존 승인 자산을 건드려야 함
- 다른 게임의 방법을 가져와야 할 가능성이 있음
- 테스트 결과가 서로 모순됨
- 실제 런타임 검증 없이는 결론을 못 냄

반환 내용에는 가능하면 다음을 포함합니다.

- 확인된 사실
- 재현 가능한 근거
- 수정/조사한 파일
- 실패한 접근
- 선택지가 있다면 각 선택지의 영향

## 6. Sol 최종 검토

Luna 결과를 받았다고 바로 완료하지 않습니다.

Sol은 최소한 다음을 확인합니다.

1. 작업 범위 준수
2. 다른 프로젝트 침범 여부
3. diff
4. 테스트
5. 기존 성공 자산 보존
6. 필요 시 런타임 검증
7. 최종 산출물 재조회

## 7. 프로젝트별 설정

실제 프로젝트에서는 `AGENTS.md`와 프로젝트 로컬 `.codex/agents/` 설정으로 이 정책을 구체화할 수 있습니다.

게임마다 별도의 `luna_reader`와 `luna_worker`를 두어 작업 루트와 금지 범위를 명시하는 것을 권장합니다.
